## 一、我方翻译实现盘点

本项目有 **两条独立翻译链路**，隐私特性差异很大，须分别分析。

### 链路 A：Google + Bing 双引擎（`translate.rs`）

**入口**：`translate_text`（`src-tauri/src/translate.rs:405`），由前端 `TranslatePanel` invoke 调用。

**数据流向**：

| 引擎 | 目标服务器 | 端点 | 数据发出内容 |
|---|---|---|---|
| Google | `translate.googleapis.com`（Google） | `/translate_a/single?client=dict-chrome-ex`（`translate.rs:86`） | `q` 参数 = 用户原文全文（`translate.rs:89`） |
| Bing | `cn.bing.com`（Microsoft） | `/ttranslatev3`（`translate.rs:237`） | `text` 字段 = 用户原文全文（`translate.rs:243`） |

**关键事实**：

1. **用户原文全文发给第三方服务器**（Google 或 Microsoft）：双引擎并行双发（`translate_with`，`translate.rs:336`），`text` 完整复制后各发一份——即同一段文字**同时**发到 Google 和 Bing 两台服务器（`translate.rs:345-357`）。
2. **无本地缓存此链路结果**：`translate_memory.rs`（`MEMORY_KEEP = 5000`，`translate_memory.rs:80`）只缓存 opencode AI 翻译结果（模型键为 AI 模型名），链路 A 结果**不走**该缓存（`translate_memory.rs` 文件注释：`// 持久化「模型 + 归一化原文 → 译文」`，无 `translate_with` 写入调用）。
3. **UA 伪装**：`translate.rs:17` 硬编码 `CHROME_UA`（Chrome 142 UA 字符串），所有请求以此身份发出，对第三方服务器伪装成 Chrome 翻译流量，透明性低。
4. **密钥/凭据**：无 API key 机制——Google 端点免 key（`client=dict-chrome-ex` 是公开端点）；Bing 端点从网页 HTML 抓会话参数（IG/IID/key/token，`translate.rs:200-215`），参数存内存（`BING_SESSION`，`translate.rs:141`），30 分钟过期，不落盘。
5. **日志**：`log::info!("[translate] 并行双发成功")`（`translate.rs:364`）只记状态，**原文不出日志**；Bing 会话参数也不入日志。
6. **设置键**：`translate_engine`（默认 `google`，`contracts.rs:95`）、`translate_target`（默认 `zh-CN`，`contracts.rs:96`）、`translate_timeout`（默认 15s，`contracts.rs:97`）。

**隐私风险小结（链路 A）**：
- 🔴 **用户原文全文双发 Google + Bing**（并行双发，`translate_with` 同时 spawn 两路），且 UA 伪装，第三方服务器可识别内容。
- 🟡 **无本地结果缓存**，每次翻译都重发全文，重复内容（常见 UI 文案）反复发送。
- 🟡 **无用户可见的"内容去了哪里"披露**（设置界面 `translate_engine` 只标"翻译源"，不披露数据流向）。

### 链路 B：本机 opencode AI 翻译（`webzh.rs` + `translate_memory.rs`）

**入口**：`opencode_translate_batch`（`webzh.rs:220`），由前端 `shift-browser-action-translate` 整页汉化流程调用，逐批发给本机 opencode（端口 4096）。

**数据流向**：

| 环节 | 数据发出 | 备注 |
|---|---|---|
| 收集 | `page_collect_translatable` 注入 JS 扫 DOM，原文留在前端 | 不出本机 |
| 翻译 | 原文发给**本机** opencode（4096），不出发 | `webzh.rs:18` 注释："页面内容不出本机" |
| 缓存 | 命中 `translate_memory`（SQLite，本机），原文+译文存本地 | `MEMORY_KEEP=5000`，超限按命中数/时间裁剪 |
| 凭据 | 从 `/proc` 读 opencode serve 环境变量，不落盘 | `webzh.rs:19` |

**隐私特性（链路 B）**：
- ✅ 原文**不出本机**（只走本机 4096）
- ✅ 结果**本地落盘**（SQLite `translate_memory` 表，有 5000 条上限 + LRU 裁剪）
- ✅ 凭据不落盘
- 🟡 `translate_memory` 是 SQLite 明文存储，**本地磁盘可读**（无加密），若多用户机器/共享机器有泄露风险
- 🟡 opencode 4096 的模型本身可能走云端推理（取决于用户配置的模型，如 `opencode/muse-spark-1.3-contributor-free` 是开源模型，但推理路径取决于用户），链路 B 的"不出本机"声明依赖用户信任本机 opencode 服务行为

## 二、Brave Translate 隐私设计对照

> 信息来源：`brave-core` 源码（1.73.x 分支）+ `go-translate` README（均直接读取，无二手引用）

### 2.1 架构：自建代理，重写 URL

`brave-core` 的 `brave_translate_constants.h`：

```
kBraveTranslateOrigin[]      = "https://translate.brave.com";
kBraveTranslateScriptURL[]   = "https://translate.brave.com/static/v1/element.js";
```

`translate_script.cc` 的核心逻辑（`chromium_src/components/translate/core/browser/translate_script.cc`，直接读源码）：
- Chromium 原版把翻译请求发往 `translate.googleapis.com`；
- Brave 版通过 `AddHostLocaleToUrl` 重写：**`result.host_piece() == google_translate_script.host_piece()` → 替换为 `kBraveTranslateScriptURL`（translate.brave.com）**（`translate_script.cc:50-54`）。
- 静态资源路径也重写：`/translate_static/` → `/static/v1/`（`brave_translate.js:31`），同样打到 `translate.brave.com`。

### 2.2 `go-translate` 代理服务器（`brave/go-translate` README）

> 直接引用 `https://github.com/brave/go-translate` README：

- `go-translate` 是 Brave 自建的**翻译代理服务器**，架在 **Lingvanex On-premise 翻译服务器**之上（`lingvanex.com/translationserver`）。
- 接收浏览器发的 Chromium 格式请求，**转换为 Lingvanex 格式**发给自建 Lingvanex 容器，再把结果转回 Chromium 格式返回。
- 支持 2 个端点：`POST /translate_a/t`（翻译）和 `GET /translate_a/l`（语言列表）。
- **语言列表**：由 Lingvanex 后端返回，数量取决于 Lingvanex 支持的语言（**"108 语言"这一数字在 Brave 官方公开文档和源码中均未找到明确声明，来源是 `Brave全景借鉴方案_2026-10-14.md:107`，属二手记录，需标记未核实**）。
- 特征开关：`UseBraveTranslateGo`（默认 `FEATURE_ENABLED_BY_DEFAULT`，`brave_translate_features.cc:16`）。

### 2.3 遥测去除

`brave_translate.js` 的 `processJavascript`（`brave_translate.js:44-48`）：
- 把 Chromium 翻译引擎内置的 `gen204` 遥测请求（`text.replaceAll('"//"+po+"/gen204?"+Bo(b)', ...)`）替换为**空 SVG data URL**——即**主动禁用遥测上报**。

### 2.4 "不存内容、删 IP"

- 来源：`Brave全景借鉴方案_2026-10-14.md:67`："自研隐私翻译（108 语言；Lingvanex 托管自有基础设施；不存内容、删 IP）"。
- 该说法在 `brave-core` 源码中**未找到直接对应的配置项**（`kBraveTranslateOrigin` 是自有域名，`go-translate` README 未明确写"不存内容"或"删 IP"策略），属于 Brave 官方隐私声明口径（需在 Brave 隐私政策文档中核实，**当前网络受限，无法直接访问 brave.com/translate**），**标记：未核实，来源为项目内文档转述**。
- "删 IP"含义：`go-translate` 作为代理层，请求经 Lingvanex 自建容器处理，理论上 Brave 可控制是否保留客户端真实 IP（是否保留取决于 go-translate 实现，当前代码只读了 README，**具体 IP 处理逻辑未从源码中确认，标记未核实**）。

### 2.5 与我们对照表

| 维度 | Brave | 我们（链路 A：Google+Bing） | 我们（链路 B：opencode） |
|---|---|---|---|
| 翻译引擎 | 自建代理 → Lingvanex | Google 免费端点 + Bing 网页端 | 本机 opencode（4096） |
| 原文去向 | Brave 自建服务器（内容是否落盘未核实） | **第三方（Google/Microsoft）双发** | 本机（不发第三方） |
| 结果本地缓存 | 未见 | **无**（链路 A 不走 `translate_memory`） | 有（`translate_memory`，5000 条） |
| 遥测 | 主动禁用 gen204 | 无遥测 | 无遥测 |
| 语言覆盖 | Lingvanex 后端（数量未核实） | Google/Bing 各自语言集 | 取决于 opencode 模型 |
| 凭据 | 无需用户凭据 | 无需 API key（公共端点） | 本机 opencode 密码（`opencode_password` 设置键，`contracts.rs:81`，mask 读） |
| 内容留痕风险 | 中（自建，是否落盘未核实） | **高**（第三方服务器，双发，UA 伪装） | **低**（本地，明文 SQLite 为余量风险） |

## 三、差距分析与可借鉴项

### 3.1 差距清单

| # | 差距项 | 现状（file:line） | 借鉴方向 | 实施代价 |
|---|---|---|---|---|
| G-1 | 链路 A 原文双发第三方（Google+Bing 同时收） | `translate_with`（`translate.rs:345-357`） | 默认改单引擎或改本机优先；披露数据流向 | 低（引擎逻辑已有单引擎分支，改默认 + UI 披露文案） |
| G-2 | 链路 A 结果无本地缓存 | `translate_memory` 只存 opencode 结果，链路 A 不写入 | 把链路 A 结果也写入 `translate_memory`（键加引擎维度，如 `google`/`bing`） | 中（新增写入路径 + 键维度扩展，需 `contracts.rs` 加 `translate_memory_max` 或复用 `MEMORY_KEEP`） |

| G-4 | UA 伪装降低透明性 | `CHROME_UA` 硬编码（`translate.rs:17`） | 在披露卡中写明"使用 Chrome 翻译端点，UA 为 Chrome"；或换为独立 UA 标识 | 低 |
| G-5 | `translate_memory` 明文存储 | `translate_memory.rs:80` SQLite 无加密 | 待条件：本地安全边界清晰后可评估 SQLCipher；或文档注明风险 | 中/高 |
| G-6 | 双引擎"并行双发"无"只取首选"选项 | `translate_with`（`translate.rs:336`）固定双发 | 增加 `translate_dual_mode` 设置（`single`/`dual`），single 模式只发首选引擎 | 低（逻辑已支持单引擎分支，需 settings 新键） |

### 3.2 不建议借鉴项（说明理由）

| 项 | 理由 |
|---|---|
| 自建 go-translate 代理 + Lingvanex 容器 | Brave 有完整基础设施团队，我们单人项目不划算；链路 B（opencode）已覆盖"内容不出本机"核心诉求 |
| 复制 Brave 的 URL 重写模式 | 我们的架构是 Tauri 客户端，不是 Chromium 内核，无 `translate_script.cc` 的上下文，不通用 |
| `gpc_header` 默认开（`contracts.rs:88`，默认 `true`） | 已有，不属于翻译隐私范畴，与 G-1~G-6 无关 |

## 四、倾向性建议（不骑墙）

### ✅ 做（低成本、高隐私收益）

1. **G-1 改默认单引擎 + 数据流向披露**（`translate_dual_mode: single` 默认值）
   - 当前双发意味着同一内容发给 Google 和 Bing 两家第三方，是链路 A 最大的隐私缺口。
   - 改动：`contracts.rs` 新增 `translate_dual_mode`（`single`/`dual`，默认 `single`），`translate_with` 按此分支；设置界面同步。
   - 代价：1 个 settings 键 + `translate.rs` 改 5 行 + 单测。
   - 收益：单发模式下次翻译只发一家，且默认行为可从 UI 明确感知。

2. **G-3 数据流向披露卡**
   - 在设置界面翻译节加说明：选择 google/bing 时"原文将发送至 Google/Bing 服务器"；选择 opencode 时"原文不出本机"。
   - 代价：纯 UI 文案 + `SettingDef.desc` 更新。

3. **G-2 链路 A 结果写 `translate_memory`（引擎维度键）**
   - 把 `translate_google` / `translate_bing` 的结果也写 `translate_memory`，键加 `engine` 字段（`google`/`bing`），避免重访/常见文案重复发送。
   - 代价：`translate_memory.rs` 加 `engine` 列 + 查询/写入路径，中等。
   - 收益：隐私（减少第三方请求频次）+ 速度（命中缓存直接返回，不发起网络请求）。

### ⏸️ 待条件

4. **G-5 `translate_memory` 加密**
   - 待条件：确认目标用户是否有多用户/共享机器场景；若有，再评估 SQLCipher 或应用层加密（代价高，当前明文 SQLite 是合理取舍）。

### ❌ 不做

5. **自建翻译代理服务器**
   - 个人项目没有基础设施预算；链路 B（opencode 本机）已覆盖隐私核心诉求，Google/Bing 作为快速路径保留价值。
