# ShiftBrowser（CEF 版）错误排查指南

> 2026-10-28 建。起因：导航卡死整窗无响应，因为没有任何证据，排查绕了一大圈。

## 一、出错了先做这一步

```bash
bash scripts/collect-logs.sh
```

产出 `/tmp/shift-logs-<时间>.tar.gz`，直接把这个文件发出去就行。里面打包了：

| 文件 | 内容 | 什么时候看 |
|---|---|---|
| `logs/Shift Browser.log` | 主日志（info 级，可提到 debug） | 正常流程走到哪一步 |
| `logs/stdio.log` | **进程 stdout/stderr**，CEF/Chromium 的 CHECK、GPU、渲染进程崩溃全在这 | 崩溃/黑屏/图形问题 |
| `logs/*.log.1~3` | 主日志轮转（单文件 10MB，留 3 份） | 崩溃发生得早，当前文件已滚过 |
| `errors.log` | **结构化错误流水**：`module=... detail=... ctx{...}` | 定位是哪个模块出的错 |
| `diagnostics.txt` | 错误计数 + 最近 30 条错误 | 快速扫一眼 |
| `panic.log` | Rust panic（线程/位置/载荷/backtrace） | 程序逻辑炸了 |
| `crash.log` | 致命信号（SIGSEGV/SIGABRT/SIGBUS/SIGILL） | 原生崩溃 |
| `system.txt` | 系统/内存/进程/安装位置/版本 | 环境问题 |

## 二、日志级别

```bash
SHIFT_LOG_LEVEL=debug shift-browser    # 排查用
SHIFT_LOG_LEVEL=trace shift-browser    # 极致详细（很吵）
```

## 三、错误机制怎么用（写代码时）

### 1. 上报一条带上下文的错误

```rust
crate::err_report::AppError::new("cef.navigate", format!("load_url 失败: {e}"))
    .ctx("url", url)
    .ctx("tab", tab_id)
    .report();
```

`module` 用点号分层（`cef.*` / `db.*` / `gtk.*` / `net.*`），便于按模块统计。

### 2. 包住可能 panic 的代码（尤其 FFI 边界）

```rust
let v = crate::err_report::guard("cef.callback", "on_load_start", || {
    // 原逻辑
}, ());
```

CEF 回调是 `extern "C"`，Rust panic 穿过去是 UB——进程会静默消失、没有栈。所有 CEF handler 都应该经 `guard`。

### 3. 锁纪律（自动检测）

`shell::lock_state` 返回 `TrackedGuard`，自动打两类警告：

```
[lock] 等锁 320ms：HashMap<String, Browser>（线程 tokio-rt-worker）
[lock] 持锁 480ms：HashMap<String, Browser>（线程 CrBrowserMain；持锁调 CEF/GTK 是死锁前兆）
```

**看到「持锁 >100ms」就要改**：锁里只 clone 句柄/数据，放锁后再调 CEF/GTK。

## 四、常见症状对照

| 症状 | 大概率原因 | 看哪里 |
|---|---|---|
| 窗口卡死、GNOME 报「无响应」，强制退出后退出码 **137** | **死锁**（SIGKILL 是强退发的，不是崩溃） | 主日志找 `[lock]` 警告；gdb 抓栈看 `Mutex::lock` |
| 进程静默消失、无任何日志 | panic 穿过 FFI 边界，或 SIGKILL | `panic.log`、`dmesg` |
| `crash.log` 有 SIGSEGV | 原生崩溃 | gdb + core dump |
| 页面白屏/黑屏 | GPU/渲染进程 | `stdio.log` 的 `ERROR:gpu` / `renderer` |
| 书签/面板不刷新 | 数据推送链路断了 | 主日志找 `[cef]` 对应模块 |
| `errors.log` 里某模块计数暴涨 | 该模块持续失败 | 按 module 过滤看 ctx |

## 五、典型案例：F-CEF-35 导航卡死（2026-10-28）

**现象**：点书签 → 窗口卡死 → GNOME「无响应」→ 强制退出 → 退出码 137。

**排查过程**：
1. `crash.log` 空白、`panic.log` 无新增、`dmesg` 无 OOM → 不是崩溃，是**卡死**
2. 前台 `wait` 拿到退出码 **137**（SIGKILL）→ 确认是强退杀的
3. `gdb -p <pid>` 抓栈：CEF UI 线程卡在 `run_toolbar_js` 等 `BROWSERS` 锁
4. 顺着栈找到：`handle_action` 的 nav 分支**持锁调 `frame.load_url`**，
   `load_url` 同步触发 `on_loading_state_change` → `run_toolbar_js` → 再拿同一把锁
   = **同线程自死锁**

**修法**：所有导航挪到锁外（`navigate()`），锁内只 clone 句柄。

**教训（已固化成机制）**：
- 锁里只取数据，绝不调 CEF/GTK
- CEF 回调里的延迟逻辑用独立线程，不要同步投递 GTK 主线程
- `spawn_local` 只能 MainContext 所属线程调，tokio 线程调必 panic

## 六、给 AI 的提示

- 报错前先 `collect-logs.sh`，**不要**让用户描述现象——日志里通常已经有了
- `grep "\[lock\]"` 是查死锁最快的入口
- `grep "module=" errors.log` 看错误分布
- 进程退出码：0=正常，1=错误退出，134=SIGABRT，137=SIGKILL（强退），139=SIGSEGV
