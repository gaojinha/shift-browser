## 三、五条真实缺口（实施蓝图）

### 🔴 缺口 1：读能穿透，写不能穿透（读写不对称）

**取证**
- 读侧 `read_page` **有** `shadow` / `iframe` 参数（`read.rs:52-53`），遍历逻辑在 `page_read.js:162`（shadowRoot）、`page_read.js:183`（contentDocument）
- 写侧 `page_action.js` 定位入口只有 `var _docQsa = Document.prototype.querySelectorAll`（line 19），**全部 3 处调用都锁 `document` 主文档**：check（line 41）、key（line 72）、交互预检（line 88）
- **无任何 shadowRoot / contentDocument 字样**

**脑会卡在哪**：现代前端大量用 Web Components（shadow DOM）与 iframe（登录框、支付页、地图、第三方挂件）。脑 `read_page` **看得见**里面有什么，一 `action/click` 就 `not_found`。
**这是最气人的死法：能看见，点不着。**

**接口设计**（给 `action/*` 统一加两个可选参数，向后兼容）

```json
{ "selector": "#submit", "index": 0,
  "pierce": true,                          // 递归穿透开放 shadow root
  "frames": [0, "#login-box"] }            // 同源 iframe 逐层下钻路径（数组元素：数字=第 N 个，字符串=选择器）
```

> ⚠️ 接口修订（v2.1）：初版写法 `frame: "0#inner"` 用 `#` 做嵌套分隔符，与 CSS id 选择器冲突（`"#login-box"` 无法区分是"第 0 层"还是"id 为 login-box"）。改为**数组逐层表达**，无歧义、可任意嵌套。

**实现要点（关键：改动高度集中）**
1. `page_action.js` 新增两个占位符 `__PIERCE__` / `__FRAME__`，`actions.rs` 侧按 `bool_arg` / `str_arg` 替换（照 `read.rs:79-80` 现成范式）
2. 新增定位函数 `qsaDeep(sel)`：先按 `frames` 数组逐层下钻（同源 `contentDocument`），再按 `pierce` 递归收集 shadowRoot 内的匹配
3. **替换 3 处 `_docQsa.call(document, ...)` 调用点即可**（check / key / 交互预检）——**共用预检是 click/fill/hover 的公共入口，改这一处，三个动作全部获得穿透能力**（行号锚点 @2026-09-26：39 / 72 / 88）
4. ⚠️ **技术坑**：`visible()`（line 28-36）用 `window.getComputedStyle`。元素若在 **iframe 内**，`window` 指向主文档，样式取错。必须改成 `el.ownerDocument.defaultView.getComputedStyle(el)`，空则回退 `window`
5. ⚠️ **能力天花板（必须诚实告知调用方）**：**跨源 iframe 进不去**。`contentDocument` 对跨源返回 `null`（`page_read.js:183-190` 已实测 `cross++` 计数）。跨源 iframe 只能靠键盘/坐标绕，不能靠穿透。**返回体里 `frame_cross_origin: true` 要显式带上**，别让脑以为是自己 selector 写错了

**安全边界**：新增参数全部可选、缺省 `false`/`""`，**不改变任何现有默认行为**；`api_agent_actions` 闸门、密码框拒绝规则原样不动

**测试**：`pierce` 命中 shadow 内元素 / `frames` 命中同源 iframe / 跨源返回 `frame_cross_origin` / 非法 frames 路径报 `bad_selector` / 旧调用（不带新参数）行为逐字节不变

**工作量**：**2.5 人日**（读侧已有可移植逻辑，主要成本在穿透函数 + 样式取窗修正 + 回归）

### 🔴 缺口 2：只有 CSS selector 一种瞄准方式

**取证**
- 全部交互定位入口 `page_action.js:88` 是 `_docQsa.call(document, SELECTOR)`；`SELECTOR` 来自 `actions.rs` 的 `required_selector(req)`，**拿不到直接报错**
- 注册表 43 条能力里，**没有"找元素"这一类**——只有"对某 selector 操作"

**脑会卡在哪**
- `<canvas>` 画的界面（图表、地图、签名板）→ 零元素可查
- `div.x1f2a` 这类构建产物 hash class → 改版即失效
- 无语义 class 的老页面 → 只能挨个试
- 脑手里只有 `read_page(mode=text)` 的整块文本，**没法把它变成一个可点的东西**

**接口设计（最高杠杆：给手加一只"眼睛"）**

新增 **`action/find`**（Risk=Read，只读）：

```json
// 三种瞄准方式
{ "text": "提交订单" }                        // 按可见文本（trim + 归一化空白）
{ "role": "button", "name": "登录" }         // 按无障碍角色 + 名称（最稳）
{ "selector": "#submit" }                    // 沿用 CSS
// 通用可选
{ "nth": 0, "exact": false, "within": "form.order", "visible_only": true,
  "pierce": true, "frames": [0] }
```

返回：
```json
{ "ok": true, "data": {
  "found": 2, "returned": 1, "nth": 0,
  "tag": "button", "role": "button", "text": "提交订单",
  "enabled": true, "visible": true,
  "rect": { "x": 412, "y": 688, "w": 96, "h": 40 },
  "selector": "form.order > button[type=submit]:nth-of-type(2)",
  "path": "form.order[2] > button"
} }
```

**为什么这是最优解**：**不改动任何现有动作**，只加一个"找"（只读）。脑"找"一次拿到稳定 selector 或坐标，再交给现成的 `action/click` / `action/fill`。
**瞄准的活交给脑，手只负责找得准** —— 这正是第一节的边界。顺带白送 canvas 支持：拿 `rect` 坐标，脑可走坐标路线或请人点一下。

**实现要点**
1. `page_action.js` 新增 `ACTION === 'find'` 分支（**必须放在 line 86 的共用预检之前**，因为 find 允许"找不到"是合法结果，不能走 `not_found` 早退）
2. 定位顺序：`selector` 精确 → `role+name`（遍历可访问性属性）→ `text`（遍历元素取 `innerText` 归一化后比较）
3. 返回 `selector` 时**要生成稳定路径**（`tag:nth-of-type` 链），不要把随机 class 塞回去
4. 复用缺口 1 的 `qsaDeep`，`pierce` / `frames` 语义完全一致
5. `rect` 取 `getBoundingClientRect()`，**同源 iframe 内元素换算坐标**要加 iframe 自身偏移（`frameEl.getBoundingClientRect()`），否则脑拿到的是 iframe 内局部坐标，一击就偏
6. ⚠️ **TOCTOU 竞态（v2.1 新增）**：SPA 重渲染可能使 find 返回的 selector/path 在下一次 click 前已失效。脑侧规约：**find 与后续动作必须紧邻调用，中间不得插入 navigate/长等待**；B3 落地后允许 `action/click` 直接接受 find 返回的 `path` 字段，消除一次往返。

**安全边界**：Risk=Read（只读，不改页面），**走 `api_readonly` 链路即可，不挂 `api_agent_actions` 闸门**——只读模式下脑也必须能"找"，否则只读等于失明。泄露面通过返回体限量控制（nearby ≤10 条、文本截断 40 字、跨源 iframe 只报 `frame_cross_origin` 不吐内容），而非闸门。

> ⚠️ 风险分类修订（v2.1）：初版写"Risk=Read 但受 `api_agent_actions` 约束"，自相矛盾。定为**纯 Read**。

**测试**：文本命中 / role 命中 / nth 越界 / 找到多个（`found>1` 要如实报，不要假装唯一）/ 零命中 / shadow 内命中 / canvas 页返回 `found:0` + 页面无可点元素提示

**工作量**：**3 人日**

### 🟠 缺口 4：`action/wait_for` 只能等出现/消失/加载

**取证**（`actions.rs:102-145`）
```rust
if !matches!(condition, "appear" | "gone" | "load") {
    return AppError::validation("condition 可选 appear / gone / load").error_json();
}
```
脚本侧（`page_action.js:37-44`）也只有 `load` / `gone` / `appear` 三分支。

**脑会卡在哪**：等"价格"或"搜索结果条数"出来——**元素一直存在，只是文本在变**。
现在只能 `appear`（立刻满足，等于没等）或 `gone`（要它消失）。于是脑被迫用 `wait(ms)` 盲等 → 又慢又不可靠。

**接口设计**（**只加枚举值，不改原三值语义，向后兼容**）

```json
{ "condition": "text",  "selector": ".price", "expect": { "op": "contains", "value": "¥299" } }
{ "condition": "enabled", "selector": "button.submit" }
{ "condition": "idle",  "quiet_ms": 500 }        // 等网络 + DOM 静默，替代盲等
```

| condition | 判定 | 替代了什么 |
|---|---|---|
| `appear`/`gone`/`load` | 现状，**行为不变** | —— |
| `text` | 元素可见文本满足 `expect`（`contains`/`equals`/`regex`） | 盲等数字 |
| `enabled` | 元素存在且 `!disabled` 且可见 | 盲等数字 |
| `idle` | 无 in-flight 请求 + DOM 连续 `quiet_ms` 未变 | 盲等数字（**提速关键**） |

**实现要点**
1. `CONDITION` 占位符**已存在**（line 17），Rust 侧只需扩 `matches!` 白名单 + 传 `expect`（复用 `__VALUE__` 占位符即可，**不新增占位符**）
2. `text`：`el.innerText` 归一化（压缩空白）后按 `op` 比较；`regex` **必须 try/catch**，非法正则返回 `bad_selector` 而非让脚本崩
3. `idle`：挂 `fetch` / `XMLHttpRequest` 计数器 + `MutationObserver` 节流计数，`quiet_ms` 内两者都为 0 才算 met
   ⚠️ **持久化坑（v2.1 新增）**：`wait_for` 是 Rust 侧每 250ms 重新 eval 整段脚本（`actions.rs:127-143`）。计数器若在每次 eval 里装了又拆，跨轮询的 in-flight 计数永远丢失，`idle` 形同虚设。**计数器必须挂到 `window.__shiftIdle` 页面级持久对象**：首次 eval 检测不存在才安装包装，后续 eval 只读计数；超时/命中后的最后一次 eval 负责清理恢复原函数。
4. `wait_for` 是**轮询**结构（`actions.rs:127-143`，250ms 一跳，超时上限 60s），轮询上限不变

**安全边界**：只读判定；但 `idle` 会在页面注入 `fetch` 包装——**须在 `finally` 恢复原函数**，避免污染页面

**测试**：四个新 condition 各一条 / 非法 `op` 报 `bad_selector` / 非法正则不崩 / 旧三值行为不变 / `idle` 在长轮询页上正确超时

**工作量**：**1.5 人日**（占位符已就位，比原估少）

### 🟠 缺口 5：没有"直接打字"的通道

**取证**
- `action/key`（`page_action.js:67-84`）：`KEY` 只能单键，派发 `keydown`/`keypress`/`keyup`
- `action/fill`（line 108-116）：**强制要 selector**（`required_selector`）
- 组合键无处表达——`Ctrl`、`Shift` 无修饰符字段

**脑会卡在哪**
- `contenteditable` 富文本（不带 id 的编辑器）
- 快捷键唤起的搜索框（按 `/` 弹出的命令面板、AI 对话框）
- 全页无可用 selector 的输入场景

**接口设计**

```json
{ "text": "hello", "clear": true }              // action/type：向当前焦点直接输入
{ "key": "Enter", "modifiers": ["Control"] }     // action/key 扩展组合键
{ "key": "a", "modifiers": ["Control", "Shift"] }
```

**实现要点**
1. `ACTION === 'type'` 分支：向 `document.activeElement`（或 body）逐字符输入。
   ⚠️ **核心技术修正（v2.1）**：合成事件 `isTrusted=false`，浏览器**不执行默认行为**——只派发 `keydown/beforeinput/input` 事件**不会把字符写进输入框**。正确做法按目标分两类：
   - `input` / `textarea`：用 **native setter** 写值——`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(el, newVal)`（绕过 React 对 value 的受控追踪），每字符写一次后派发 `new InputEvent('input', {bubbles:true, inputType:'insertText', data:ch})`
   - `contenteditable`：用 **Selection/Range API** 在光标处 `insertNode` 文本节点并移动选区（或 `document.execCommand('insertText', false, ch)` 兜底），再派发 `input` 事件
   必须逐字符走完整流程——一次性赋值会被 Vue/React 受控组件在下次渲染时覆盖回去
2. `clear: true` 先全选（input 用 `el.select()`，contenteditable 用 `selectAllChildren`）再删除
3. `key` 扩展 `modifiers` 数组 → JS 侧 `new KeyboardEvent('keydown', {ctrlKey, shiftKey, altKey, metaKey, key})`
   ⚠️ 边界：合成 KeyboardEvent 只对**页面 JS 监听器**有效（命令面板、`/` 唤起搜索框等场景成立）；对**浏览器原生快捷键**（如 Ctrl+T 开标签）无效——那不是页面事件能触达的
4. ⚠️ **新占位符**：`__MODIFIERS__`（`actions.rs:48-51` 追加一条 replace）
5. ⚠️ **安全**：type 往页面输入的是**纯字符串**（沿用 fill 的铁律：不执行）。**绝不接受任意 JS 表达式**

**安全边界**：Risk=Write，受双闸门；**`type` 不得绕过密码框拒绝规则**——若 activeElement 是 `input[type=password]`，须沿用现有拒绝逻辑返回明确错误

**测试**：普通输入框 / contenteditable / `clear` 生效 / `Ctrl+A` 修饰键位正确 / 输入到密码框被拒 / 空 `text` 报错

**工作量**：**1.5 人日**

### 🟡 缺口 6：失败时手不告诉脑"页面上到底有什么"

**取证**：`page_action.js:89-95` 失败只回三态 —— `not_found` / `bad_selector` / `not_visible` / `disabled`，**零现场信息**。

**脑会卡在哪**：拿到 `not_found` 只能瞎猜——选择器写错了？元素在 iframe 里（缺口 1）？页面还没加载完（缺口 4）？压根没这个按钮？
**猜错就重试，重试还错，脑就卡死了。** 这是自动化"卡住不动"最主要的原因。

**补法**：并入 `action/find` 的失败路径，**几乎零额外成本**

```json
{ "ok": true, "data": {
  "found": 0,
  "diagnose": {
    "reason": "not_found",
    "nearby": [ { "tag": "div", "text": "提交订单", "class": "btn-primary" },
                { "tag": "span", "text": "订单金额", "class": "amount" } ],
    "same_text": [ { "selector": "button.txt-submit", "rect": {...} } ],
    "in_iframe": [ { "frame": "0", "has_text": "提交订单", "same_origin": true } ],
    "hint": "页面有 2 个 iframe 含'提交'字样，试 frame=0"
  }
} }
```

**实现要点**
1. `not_found` 时对**同父容器**取前后各 3 个兄弟元素摘要（tag + 可见文本截 40 字 + class 前 2 段）
2. 全文搜 `text` 关键词，命中处回报其稳定 selector 与 rect
3. 扫 `iframe` 列表，比对同源与否（**跨源只报"有此 iframe 且含该文本（经标题推测）"，不谎报可点**）
4. **诊断只读、限量**：`nearby` 上限 10 条、文本截断，**不许把整页文本倒出来**（否则违反最小暴露原则，且会撑爆 token）

**测试**：`not_found` 附诊断 / iframe 命中提示 / 跨源不谎报 / 诊断体积上限 / 无敏感信息泄露（密码框不进 `nearby`）

**工作量**：**+0.5 人日**（并入缺口 2）

## 九、加能力的固定链路（实测固化，漏一步测试就红）

每加一个能力，四步缺一不可：

1. `capabilities/registry/table_read.rs` / `table_write.rs` 加 `tool(...)` 条目（**带 Risk**）

3. handler 唯一实现（参数校验、闸门、错误分类）
4. 测试自动校验：
   - `every_capability_has_handler` —— 注册表有 → HANDLERS 必有
   - `every_handler_is_risk_classified` —— HANDLERS 有 → Risk 必有

若动了 `page_action.js` 或 `page_read.js`，额外跑交互回归（这两文件是全部动作的公共内核）。
