## 根因（perf 栈钉死）

```
gtk_main_iteration_do
  → g_main_context_iteration
  → libxcb __libc_recvmsg
  → libcef x11::Connection::HasPendingResponses()
```

`multi_threaded_message_loop=0` 时 CEF 在 GLib 主循环注册 X11 source，每次迭代都去 xcb 收消息 → 忙轮询。改成 CEF 自跑消息循环后该 source 不再挂在 GTK 主循环上。

## 三个坑（后续别再踩）

### 1. MSRV 1.77.2 不支持 `LazyLock`（1.80 稳定）

`cargo clippy` 的 msrv 检查直接报错。替代方案：
- 非 HashMap → `static X: Mutex<T> = Mutex::new(...)`（`Mutex::new` 是 const）
- HashMap → `OnceLock<Mutex<HashMap>>` + 访问函数 `fn x() -> &'static Mutex<...> { X.get_or_init(|| Mutex::new(HashMap::new())) }`

### 2. `wrap_task!` 宏必须裸名导入

cef crate 的 `wrap_task!` 是 `#[macro_export]`，但**宏内部递归调用用的是裸名** `wrap_task ! { ... }`，所以调用方必须 `use cef::wrap_task;`，写 `cef::wrap_task! {` 会报 `cannot find macro wrap_task in this scope`，并连锁报 `UiPostTask` 未定义（宏没展开）。

### 3. `multi_threaded=1` 后 CEF 回调不在 GTK 主线程

这是最隐蔽的雷。`glib::timeout_add_local*` / `idle_add_local*` / GTK widget 操作**只能在 GTK 主线程**，跨线程会 panic：

```
default main context already acquired by another thread
glib-0.18.5/src/source.rs:345
```

表现：窗口先出现，几秒后消失、进程崩，日志里 `thread=tokio-rt-worker`。

修法：新增 `gtk_ui(f)`（`gtk::glib::MainContext::default().invoke(f)`，线程安全，已在主线程则原地执行），在 CEF 回调 / tokio 线程里用它包一层，再在闭包内注册 glib 定时器。

已修 4 处：`on_before_close` 退出 idle、`close_tab` 的 200ms 标志复位、`set_bookmarks` 的刷新、`open_shell_on_main` 的补推定时器。

## 线程模型（改后）

| 线程 | 职责 | 禁止 |
|---|---|---|
| GTK 主线程 | GTK widget、glib 定时器、X11 映射 | 直接调 CEF 句柄方法 |
| CEF UI 线程 | 所有 CEF 句柄方法（窗口/视图/浏览器/frame） | 调 glib `*_add_local`、GTK widget |
| tokio 线程 | 数据库/网络 | 两者都禁；用 `cef_ui` / `gtk_ui` 投递 |

锁纪律：锁内只 clone 句柄或数据，放锁后再投递；`cef_ui`/`cef_ui_call` 一律在锁外调。
