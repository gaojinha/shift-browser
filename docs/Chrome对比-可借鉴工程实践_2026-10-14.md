# Chrome 对比 · 可借鉴工程实践清单（2026-10-14）

> 分析：王二狗（协调器）
> 方法：REA 二进制结构分析（4 份完整证据）+ 实测对比 + readelf 补充观测
> 对照物：Chrome 154.0.8037.57（官方 Linux 包） vs ShiftBrowser 当前构建（2026-10-14 21:52）
> **结论先行**：ShiftBrowser 不需要（也不应该）追 Chrome 的"全栈自研"；但 Chrome 二十年沉淀的 **发布工程纪律** 可以低成本直抄——符号剥离、独立调试文件、加固开关、组件最小化。四项都是低风险高收益。

## 二、可借鉴清单（按性价比排序）

### ★★★ P0-1：发布版符号剥离 + 独立调试文件
**Chrome 观测**：主二进制只留 1473 行动态符号（readelf 计数）；三个组件均带 `.gnu_debuglink` 指向独立调试文件（REA 证据）。
**我们现状**：主二进制 67033 行符号（readelf 计数）；`shift-browser-mcp` 8 个 `.debug_*` 段全带（REA 证据 ev_9e5a06cc…）。
**怎么做**：
1. 发布构建分离调试信息：`objcopy --only-keep-debug` 分离 → `strip` 主产物 → `objcopy --add-gnu-debuglink` 关联（配合 `--build-id`）
2. 调试文件按版本归档留存（崩溃回溯用）
3. **先审计崩溃上报链路**：若现有回溯依赖内嵌符号，先改链路再剥离
**收益**：攻击面↓ 体积↓ 逆向门槛↑；内部调试能力无损
**风险**：低（唯一注意点：崩溃解析链路）
**验收**：发布产物 `file` 无 "not stripped"；抓一个崩溃样例能解析出符号。

### ★★★ P0-2：加固开关核对（canary 等）
**Chrome 观测**：三个组件栈保护全开（REA 证据）；PIE/NX/Full RELRO 全齐。
**我们现状**：PIE/NX/Full RELRO 已达标；canary 未开——Rust 主体有语言级安全，但 **FFI 下挂的 C 依赖部分是 C 代码**。
**怎么做**：审计构建链对 C/C++ 依赖的编译参数（如 `-fstack-protector-strong`）；Rust 侧维持现状即可。
**风险**：低。

### ★★☆ P1-1：安全/稳定性组件独立化（crashpad 模式）
**Chrome 观测**：`chrome-sandbox` 代码段仅 4033 字节（suid、独立进程、极简攻击面）；`crashpad`（1.9MB）独立崩溃处理；`management-service` 独立。
**我们的痛点（自有文档）**：webview 崩溃 = 全浏览器退出；GTK 叠层 workaround 是总根源。
**方向**：崩溃收集/遥测/日志组件独立进程化、最小化，与主进程解耦。
**说明**：架构级方向，列参考不排当期。

### ★★☆ P1-2：发布资产规范
**Chrome 观测**：`CHROME_VERSION_EXTRA` 版本标识文件、每组件配调试文件、资产目录结构整齐。
**怎么做**：发布 checklist——版本标识、符号策略、调试文件归档、资产哈希清单。
**风险**：低。

### ★☆☆ P2：多进程隔离模型（长期路线）
Chrome 的 zygote/renderer 隔离是浏览器安全基石；Tauri 单进程架构是当前约束。长期架构参考，不排期。
