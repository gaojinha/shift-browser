# C-10 translate_memory 加密评估（2026-10-15）

> 来源：S-9 翻译隐私调研 G-5「待条件：确认是否多用户/共享机器；若有再评估 SQLCipher 或应用层加密」
> 性质：纯评估，不动产品代码
> 口径：本仓源码 + 实读配置；未核实项在文末如实标注

---

## 一、结论（TL;DR）

**倾向：现阶段不做 translate_memory 的列级加密；这是威胁模型决定的，不是"要不要保护隐私"的态度问题。**

三条判断：

1. **列级加密在此威胁模型下几乎不增益**——唯一能多挡的场景是"DB 文件单独泄露但密钥文件没跟着泄露"，而这个场景下数据库里还有 history / bookmarks / sessions 同样是明文，单表加密等于"漏水的桶补一个洞"。
2. **若目标是静态防护，正解是整库方案**：全盘加密（运维层，零开发成本，性价比最高）> SQLCipher 整库（高成本）> 单表列级加密（低收益）。
3. **唯一值得现在做的低成本项**：让 translate_memory **不落原文明文**（用键控 HMAC 做查询键替代 `source` 列），这是"数据最小化"，独立于密钥安全，且成本极低。建议立为 C-11（择机）。

**触发升级条件**：一旦 translate_memory 被纳入上云同步（sync 包），或出现多用户/共享机器场景 → 加密升为**必修**；但那时应沿用 sync 现成的"整包 AES-GCM 封装"，而不是改表结构。

## 二、评估对象：translate_memory 里到底装了什么

| 列 | 内容 | 敏感度 |
|----|------|--------|
| `model` | 隔离键：AI 模型名（`opencode/big-pickle`）或引擎命名空间（`engine:google:zh-CN`，C-9 新增） | 低（不含用户内容） |
| `source` | **归一化后的页面原文**（压缩空白的待译文本） | **高——用户浏览内容本身** |
| `target` | 译文 | 中（可反推原文大意） |
| `hits` / 时间戳 | 命中次数、创建/更新时间 | 低（但时间戳可侧写使用行为） |

- 容量上限 `MEMORY_KEEP = 5000` 条（`db/translate_memory.rs`）。
- 写入方：整页汉化（AI 模型路径，webzh）+ 引擎翻译（Google/Bing，C-9 新增）。
- **无任何读取原文的 UI**：`source` 只用于等值查询与命中排序，从不展示回页面。→ 这是后文"可不落明文"方案成立的前提。

## 三、现状防护与威胁模型

### 现状（实读）
- DB 文件：`app_data_dir/shift-browser.db`；目录 0700、文件 0600（`db/mod.rs`）。
- DB 加密：**无**。sqlx 只启用 `runtime-tokio, sqlite`（未开 `sqlcipher`），文件是普通明文 SQLite。
- 列级加密：仅 `passwords.password` 用 AES-256-GCM（`password_crypto`），密钥在 `master.key`（自动生成、权限 600、**与 DB 同目录**、**无需用户主密码**）。
- 上云同步（`db/sync`，第 45 章零知识）：只导出 **密码库密文 + 书签 + 会话(≤50) + 历史(≤300)**，整包用**密码库主密码**派生的 AES-256-GCM 封装。**translate_memory 不在同步包内**。

### 威胁模型对照

| 攻击者 / 场景 | 0700/0600 是否挡住 | 现有列级加密是否挡住 | **给 translate_memory 单独加密是否增益** |
|---|---|---|---|
| 同机其他 OS 用户 | ✅ 挡住 | 无关 | ❌ 已被 0600 挡，无增益 |
| 同机同用户的其他进程（恶意软件） | ❌ 挡不住 | ❌ 挡不住（master.key 同权限可读） | ❌ 密钥同用户可读，无增益 |
| 磁盘/整机被盗（无全盘加密） | ❌ | 部分（密钥也丢则无效） | ⚠️ 但 history/书签同样明文，单表加密无意义 |
| **仅 DB 文件被单独拷走（不含密钥文件）** | ❌ | ✅ 挡住 | ⚠️ **唯一有增益**的场景 |
| 全盘加密已到位 | — | — | ❌ 冗余 |

**结论**：列级加密的全部价值集中在最后那个窄场景；而该场景下整库明文的其他表更值钱，攻击者不会只盯着翻译缓存。

## 四、方案对比

### 方案 A：不动（维持明文）
- 成本：0。
- 依赖：OS 权限（0700/0600）+ 建议的全盘加密。
- 取舍：与 S-9 原文"当前明文 SQLite 是合理取舍"一致。

### 方案 B：SQLCipher（整库加密）
- 需 sqlx `sqlcipher` feature（捆绑 libsqlcipher）+ 全库迁移 + 密钥生命周期设计。
- 关键纠结点：密钥用谁？
  - 用**用户主密码**（vault）：与"未解锁时浏览器不可用"强耦合——history/书签/翻译全读不了，体验塌方。
  - 用**自动生成的 master.key**：等于"同机同用户可读"，静态防护边界与方案 C 相同，但成本高一个量级。
- 成本：**高**（依赖 + 迁移 + 解锁体验 + 全量回归）。

### 方案 C：应用层加密（仅 translate_memory，HMAC 键 + 加密值）
- 关键可行点：记忆只做"按原文查译文"，**无需保留原文明文**。
- 设计：
  - `source` 列 → `source_hash` = **HMAC-SHA256(master.key, 归一化原文)**，确定性，保住 `WHERE model=? AND source_hash=?` 等值查询；
  - `target` 列 → AES-256-GCM（随机 nonce，base64，复用 `password_crypto` 原语）；
  - 迁移：translate_memory 是**缓存**，迁移可直接清表（零价值损失），或一次性重写；
  - 密钥：复用现成 `master.key`（已在用、600、与 DB 分离）。
- 成本：**中低**（1 个迁移 + lookup/remember 改写 + 单测）。
- 收益：DB 里**不再有可读原文**（连 HMAC 也不可逆），这是"数据最小化"，独立于密钥是否泄露。
- 局限：对"同机同用户 + 能读 master.key"无效（但那种情况本就防不住），译文仍可解。
- ⚠️ **勘误（2026-10-15 实施前核实）**：原稿写"密钥复用 master.key"**不成立**。
  `db::password_crypto::get_master_key` 有单一闸门——**密码库设了主密码且未解锁时，
  主密钥只从解锁会话内存取，磁盘不可读**（`vault::is_protected` → 直接拒绝）。
  若 C-11 复用 master.key，翻译缓存会与"密码库是否解锁"耦合：锁库时 HMAC/解密全部失败，
  记忆缓存静默失效。**C-11 应改用独立密钥文件**（如 `translate.key`，自动生成、600、
  与 vault 解耦），代价是多一个密钥文件，收益是行为与锁库状态无关。

## 五、建议（明确倾向）

1. **不做方案 B（SQLCipher）**：成本与解锁语义耦合太重，收益边界与方案 C 相同。
2. **不做 translate_memory 的"纯加密"（把原文留着只加密译文）**：防不住同机读取，收益近乎为零。
3. **择机做方案 C 的"不落原文"部分**（→ 建议立 C-11）：
   - 理由：与 C-8/C-9 的隐私主线一致（不再"减少网络外发却本地落明文原文"），且是数据最小化，成本极低、迁移零风险。
   - 优先级：低（不影响功能与验收）。
4. **静态防护的性价比排序**（供全盘安全决策参考）：
   **全盘加密（运维层，0 开发）> SQLCipher 整库（高成本）> 单表列级加密（低收益）**。
5. **硬触发**：translate_memory 一旦进入 sync 包上云 → **必须加密**；直接复用 sync 的整包 AES-GCM，不改表。
