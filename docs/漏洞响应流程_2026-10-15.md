# 漏洞响应流程（轻量版）

> C-5 借鉴 Brave：人少也要有可执行的漏洞响应流程。参照 HackerOne 轻量化，裁剪到单人/小团队可维护，不照搬其赏金制度。
> 依据：《Brave全景借鉴方案》§三 / S-7 借鉴清单 v2 · C-5
> 性质：纯流程文档，无代码改动。

## 1. 报告入口

- **邮箱**：**gaojinha@163.com**（高哥 2026-10-15 拍板；已同步根目录 `SECURITY.md` 与 README）
- 报告请附：影响描述、复现步骤/PoC、涉及版本；敏感信息（凭据/密钥）不要随报告发送
- 原则：入口稳定、公开可发现；后续如需非公开渠道（PGP / 专用表单）再另行扩展

## 2. 定级标准

结合本项目安全面（开放 API 鉴权 / 密钥与口令存储 / SSRF pin / CSP / 证书与 TLS / 权限 prompt / DB 注入），按影响分级：

| 级别 | 定义 | 本项目典型例 |
|---|---|---|
| P0 Critical | 可直接远程利用，导致 RCE / 任意代码执行 / 完全接管 | 开放 API 绕过鉴权执行任意命令；SSRF pin 被绕读内网敏感数据 |
| P1 High | 可被利用获取敏感数据或权限提升 | 密钥/口令可明文读出；CSP 被绕注入脚本；权限 prompt 误放行 |
| P2 Medium | 有限影响，需特定条件或本地利用 | 单站点信息泄露；下载路径受限遍历 |
| P3 Low | 轻微 / 信息性 | 版本/配置信息暴露；非敏感信息泄露 |

> 基线参照 CVSS 3.1：P0 ≈ ≥9.0，P1 ≈ 7.0–8.9，P2 ≈ 4.0–6.9，P3 < 4.0。以「是否可被未认证远程利用」为关键加权项。

## 3. 修复时限（现实目标，非 SLA 承诺）

| 级别 | 首次响应 | 修复目标 |
|---|---|---|
| P0 | 24h | 72h 内出修复或缓解措施 |
| P1 | 3 天 | 1–2 周 |
| P2 | 1 周 | 纳入常规排期 |
| P3 | 2 周 | 视情况 |

> 单人维护的现实目标，不是对外承诺；P0 优先一切，必要时暂停其它任务。

## 4. 披露原则（负责任披露）

- 未修复漏洞**不公开**：不在 issue / commit / 公告中暴露细节
- 修复前与报告者保持单线沟通，确认修复有效
- 修复发布后告知报告者；报告者同意时公开致谢
- 披露窗口：报告后给报告者合理时间（建议 ≥30 天）再对外披露细节
- 安全面变更（SSRF pin / CSP / 鉴权 / 密钥存储）在 commit 注明安全意图，但不披露未修复缺陷细节

## 5. 响应流程

1. **接收**：报告入口收到 → 记录时间 / 渠道 / 报告者
2. **确认**：验证可复现；无法复现则请报告者补 PoC
3. **定级**：按 §2 分级
4. **修复**：按 §3 时限，走 AGENTS.md 四步走（拆解→查证→执行→验证），安全敏感改动过 `security-reviewer` 专项审查
5. **披露**：按 §4 闭环
6. **复盘**：P0 / P1 修复后沉淀到 `.learnings`（根因 + 防复发措施）

## 6. 适用范围与边界

- 适用于 Shift Browser 自身（Rust 后端 + Vue 前端 + 开放 API）
- 上游依赖（Tauri / WebKitGTK）漏洞走各自上游响应流程，本流程只跟踪「是否影响我们 + 何时升级」
- 赏金制度暂不适用（人少），记入长期（见借鉴方案 §三）
