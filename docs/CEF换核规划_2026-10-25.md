## 一、立项依据（因果链，写死）

1. **2026-10-14 实机诊断结论**（兼容性诊断报告）：
   - ShiftBrowser 与真 Chrome 154 在 **TLS 指纹（JA3/JA4）、HTTP/2 指纹** 两层是**结构性差异**：
     - GnuTLS 密码套件 29 vs BoringSSL 15，JA4 完全不同（`500acc...` vs `t13d1517...`）；
     - libsoup 帧序/伪头顺序与 Chromium 不一致；
   - 这两层**JS 层无法修复**（传输层在页面加载前就被检测方读到）；
   - 报告原话："保持 WebKitGTK/GnuTLS 网络栈的前提下：TLS/HTTP2 层矛盾无解"。
2. **Cloudflare 检测现实**：JA4 + UA 声明不符是其现成规则思路，开"激进 bot 模式"的站点直接给高分 → 真人验证、屏蔽。
3. **诊断报告第 1.4 节留了口子**："换网络栈为架构级决策，本报告不含结论" → 本规划就是这个架构级决策的正式立项。

**结论：换核（CEF = 真 Chromium）是解决 TLS/HTTP2 指纹层唯一可行的工程路径，其余层（请求头/JS/行为）仍需配套动作，见第五节。**

## 二、目标与非目标

### 目标
- G：TLS/JA3/JA4、HTTP/2 帧指纹**天然与 Chrome 一致**（换核直接达成，不用应用层伪装）
- G：AI 全链路能力（页面快照 / Agent 动作 / WebMCP polyfill / 翻译 / 扩展注入）在 CEF 路径**等价保留**
- G：Wayland 会话可正常工作（现状 DMA-BUF 缺陷导致的视频闪烁一并消解，待验证）
- G：CEF 构建可打包进生产发布物（含离线资源）

### 非目标（本期不做）
- 不做 Windows/macOS CEF（本期只 Linux；Windows 走 Tauri/WebView2，不受 TLS 指纹问题影响）
- 不做 CEF 版本跟随的自动化流水线（跟版机制在第五节 P2，人工季度评估）
- 不删 WebKitGTK 路径（回退兜底，见第六节）

### 3.2 代码注释里已沉淀的 P0 实测结论（写进规划，防止踩回头路）

1. CEF 只能走 **X11 子窗口**嵌入（`WindowInfo::set_as_child`）→ 必须在 CEF 初始化前 `GDK_BACKEND=x11` + 提前 `gtk::init()`（`main.rs` 已做）；
2. CEF 回调是 `extern "C"`，**panic 绝不能穿过 FFI 边界**，一律错误返回；
3. `_sync` 创建变体不产生 X11 子窗口（`window_handle()=1`）→ 必须用**异步** `browser_host_create_browser`，句柄在 `on_after_created` 里拿；
4. `GtkFixed` 拿不到独立 GdkWindow → 容器必须用 **`GtkDrawingArea`**；
5. 静态链入的 sqlite3 符号污染 NSS PKCS#11 → `--exclude-libs,ALL`（`build.rs` 已做）；
6. `set_as_child` 的 bounds 在 X11 下不生效（0×0 创建）→ 必须 `on_after_created` 后 `XMoveResizeWindow`（`PENDING_SIZE` 机制）。

## 五、AI 功能保留评估（2026-10-25 结论，高哥问）
