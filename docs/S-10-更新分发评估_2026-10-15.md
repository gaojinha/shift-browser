## 二、与 Brave 的差距（维度十四）

| 维度 | Brave | 我们 | 差距 |
|---|---|---|---|
| 通道 | 四通道 Release/Beta/Dev/Nightly | 单通道 | 内测/灰度无处落地 |
| 包形 | deb/rpm/**Flatpak**/snap | 仅 deb | 跨发行版覆盖窄 |
| 更新 | 自动更新 + "Relaunch to finish updating" | 手动 dpkg | 更新全靠用户主动 |
| 分发 | CI 全量矩阵 | 本地手动 | 无自动化发布 |

> 注：Brave 是 Chromium 系（WebView 与浏览器同包），我们是 Tauri + WebKitGTK，包形与更新机制不能直接照搬，只借"多通道 + 多包形 + 自动更新"的**思路**。

## 三、关键洞察：deb 与 Tauri 自动更新不兼容（评估核心）

**Tauri v2 的 updater 在 Linux 只支持自包含包形（AppImage / Flatpak），dpkg 管理的 deb 无法被 updater 原地替换**（updater 替换的是可执行文件本身，而 deb 的文件归 dpkg 系统管）。

由此推出本次评估最重要的结论：

> **"双通道"与"自动更新"是两件不同难度的事，必须分开排期。**
> - **双通道 = 命名 + 分发位**（哪个分支/tag 产出、版本号怎么标、放哪里下载）——**易**，不需要自动更新，加 CI release job 即可。
> - **自动更新 = 换包形 + 签名基建 + 更新清单托管**——**难**，且和当前 deb 包形冲突（要上自动更新，基本得切 AppImage 或 Flatpak）。

这条决定了下面的分期建议：**先做双通道（易、高价值），自动更新与 Flatpak 都往后放。**

## 四、稳定/测试双通道（推荐先做，Phase 1）

### 4.1 方案
- **stable（稳定通道）**：由 **tag**（如 `v5.9.0`）触发，产出正式版本号 deb，发 AtomGit Release。面向所有用户。
- **test（测试/内测通道）**：由 **test 分支**（如 `test`，或 master 的 nightly 节奏）触发，产出 **semver 预发布标识**版本（如 `5.9.0-test.1` / `5.9.0-beta.2`），发独立 Release（标注"内测"）。面向内测朋友。

### 4.2 为什么这样切
- **semver 预发布标识**天然隔离两通道：`5.9.0-test.1 < 5.9.0`，stable 用户绝不会误装 test 构建（为将来接自动更新留好版本号语义）。
- **正式化"Nightly 式内部通道"（维度十六）**：我们已有 5.8.3 的一体化构建安装节奏，把它固化成 test 通道 = "内部先行验证"，零额外概念。
- **不需要自动更新就能跑**：双通道本质是"打哪个包、叫什么、放哪下"，CI 加 release job 即可落地。

### 4.3 落地要点（Phase 1，均为增量、不动现有逻辑）
1. `tauri.conf.json` 版本改为可被 CI 注入（或读 `CARGO_PKG_VERSION`），test 通道追加 `-test.N` 后缀。
2. 新增 `.github/workflows/release.yml`：
   - tag `v*` → 打 stable deb → 传 AtomGit Release（`tauri build --bundles deb` + 上传）。
   - push 到 `test` 分支 → 打 test deb（版本号加 `-test.N`）→ 传内测 Release。
3. 复用现有 `package-deb.sh` 的打包逻辑（避免两处口径漂移）。
4. Release 页写清"稳定/内测"两档说明 + 安装命令（`sudo dpkg -i`）。

**成本**：小（1 个 workflow + 版本号注入 + Release 文案）。**收益**：内测朋友有专属通道、nightly 节奏正式化、为自动更新铺好版本语义。

## 五、Flatpak 可行性（建议缓做，Phase 3）

### 5.1 可行性
- Tauri v2 **支持 Flatpak 打包**（`tauri build --bundles flatpak`，底层 linuxdeploy + Flatpak builder，需 `flatpak-builder` + `org.gnome.Platform` runtime + manifest）。
- **优点**：跨发行版覆盖（不依赖各发行版仓库）、沙箱（贴合我们隐私定位）、可上 Flathub。

### 5.2 风险（浏览器场景特有，是本项的主要成本）
- **沙箱配置是硬骨头**：我们是浏览器（WebKitGTK + child webview 盖 GTK 部件），Flatpak 沙箱默认隔离网络/文件；要让下载落盘、child webview、GTK 窗口正常工作，`--share=network`、`--socket`、文件访问等要逐项放行，**放太宽违背沙箱初衷，放太窄功能坏**——需要 POC 验证，非纸面能定。
- **runtime 体积**：Flatpak 自带 GNOME runtime（含 webkit2gtk），包体比 deb 大。
- **Flathub 提交**：有审核周期与规范（图标/元数据/沙箱声明）。
- **与自动更新的关系**：Flatpak 的更新走 Flathub（不是 Tauri updater），与 4.x 的 Tauri updater 路线是**两条路**，别混。

### 5.3 结论
Flatpak 价值真实（跨发行版 + 沙箱 + 隐私叙事），但**浏览器沙箱 POC 是主要不确定项**，且和 deb/AppImage 自动更新路线不是一条路。**建议缓做**：等 Phase 1（双通道 deb）+ Phase 2（自动更新方案定案）稳定后，再单独立项做 Flatpak POC。**不阻塞当前。**

## 六、自动更新（相关，Phase 2，需换包形 + 基建）

> 维度十四的"自动更新 + Relaunch 提示"归在这里，因为它是"难"的那半。

- **机制**：`tauri-plugin-updater` = 签名密钥对（ed25519）+ `tauri.conf.json` `plugins.updater`（`endpoints` + `pubkey`）+ 更新清单 JSON + 产物托管。
- **前置基建**：① 生成并安全保管签名私钥；② 更新清单 + 产物的托管位（AtomGit Release 可承载）；③ **包形得用 AppImage/Flatpak**（deb 不行，见 §三）。
- **更新提示 UI（维度十四③）**：对标 Brave "Nearly up to date!" 文案体系——这条是纯前端，可与 Phase 2 一并做。
- **成本**：中（签名基建 + 包形切换 + updater 集成 + 提示 UI）。**收益**：用户无感更新（留存关键）。
- **风险**：包形从 deb 切 AppImage 会影响现有 `sudo dpkg -i` 安装习惯与 5.8.3 已装用户——**切换要单独拍板**，不能夹带。
