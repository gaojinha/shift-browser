# 整页汉化与翻译选中 · 实现与踩坑记录

- 日期：2026-09-26
- 状态：核心链路可用；「翻译选中」选区读取已通，完整链路待最终确认
- 触发需求：把「翻译当前页」从"发给 AI 看译文"改成"译文直接长在页面上"，并支持翻译选中内容、提速

---

## 1. 整体架构

三段式管线，全部走本机 opencode（`127.0.0.1:4096`），页面内容不出本机：

```
page_collect.js     扫 DOM，收集待翻段落 + 属性，给节点打 __sbId 标记
       ↓
opencode_translate_batch   逐批调本机 opencode，结构化 JSON 数组（id → 译文）
       ↓
page_apply.js       按 __sbId 写回；原文备份在页面上，支持一键还原
```

编排（分批、进度、停止、分批写回）在前端 `src/stores/ai.ts`；Rust 侧 `webzh.rs` 只提供可单测的能力块。

关键设计：

- **定位靠标记不靠顺序**：整页翻译要跑几十秒，期间页面可能自己动（轮播/虚拟列表/懒加载/SPA 路由）。靠 `__sbId` 找节点，页面动过的节点跳过（`mismatched` 计数），绝不错位写。
- **必须可还原**：这是在改别人的页面。原文按整段 `innerHTML` 备份，还原时连 `<a>`/`<span>` 一起回来。
- **段落是翻译单位**：按块级元素整段收集（`p/h1-h6/li/td/blockquote/...`），不按叶子文本节点。

## 2. 踩坑记录（按发现顺序）

### 2.1 前端解包少一层 `data` —— 「找不到要翻译的内容」

**现象**：点「翻译当前页」永远提示"这页没找到需要翻译的文字"，任何页面都这样。

**根因**：后端三条命令返回 `{ok, msg, data}` 包装，而 `invokeOk` **只做错误归一化、不解包**。前端写的是 `col.segments`，实际拿到的是 `{ok,msg,data}`，`col.segments` 恒为 `undefined`。

**为什么测试全绿**：
- 手测走 api.sock，那条路协议层会自动展开 `{ok,data}` → 正常；
- 前端单测的 mock 是**自己编的裸结构**，跟真实返回不一致 → 自证清白。

**教训**：mock 必须照抄真实返回结构；同一个命令的两条调用路径（Tauri invoke / api.sock）返回形状可能不同，两条都要测。

**修复**：`ai.ts` 加 `zhCall<T>()` 统一解包，`ok:false` 抛错（原实现连这个判断都漏了）；mock 全部对齐真实结构；`webzh.rs` 加契约测试钉死字段名。

### 2.2 `ask_once` 的 baseline 取值时机 —— 每批都"模型输出无法解析"

**现象**：真机每批都失败，日志 `批次翻译失败：模型输出无法解析，前 200 字：（空）`；RFC 9110 跑 30+ 批全军覆没。

**根因**：`baseline_ids()` 在 `POST prompt_async` **之后**取。本地 opencode 建消息极快，刚发出的这条被算进基线，它自己的 delta 全被 `fold_event` 当历史丢掉 → 模型照翻，代码收不到，返回空串。

**为什么没测出来**：这是 race。测试环境赶在消息落库前取到空基线，侥幸通过。

**修复**：baseline 挪到 POST **之前**（对齐 `drive` 的做法）。新增 `live_同会话连翻多批都拿到译文` 盯这个点。

### 2.3 `cleanup` 删了 `__sbOrig` —— 重复汉化把原文永久破坏

**现象**：连点两次汉化，还原后只能回到"上一轮译文"，回不到真原文。

**根因**：收集脚本开头无条件 `delete n.__sbOrig`，把 apply 存的原文备份清掉了。第二次 apply 于是把"上轮译文+存成原文备份"。

**修复**：收集阶段**一律不碰** `__sbOrig`；发现页面已汉化则先还原回原文再重新收集。原文备份的生命周期由「还原」掌管。

### 2.4 段落里有内联标签就整段漏收 —— 「汉化率不高、很多没翻」

**现象**：用户反馈页面大部分还是英文，看着像没翻。

**根因**：收集条件是"父元素没有元素子节点"。段落里只要出现一个 `<a>`/`<span>`/`<b>`，整段主体文字全被跳过。

**实测证据**（RFC 9110）：收集到 1708 段，其中 **66% 是 <20 字碎片**（"Status:"、"9110"、"97"），Abstract 那种整段正文**一个字没收到**。翻成功的那 292 处质量其实很专业（"互联网工程任务组"、"确立保护空间（Realm）"）——不是模型不会翻，是内容压根没送去翻。

**修复**：按块级段落整段收集，从外到内扫并给后代打 `covered` 标记。

### 2.5 属性收集复用了 `SKIP_TAGS` —— 表单 placeholder 全丢

**根因**：属性收集沿用了文本收集的跳过名单，而里面有 `INPUT`/`TEXTAREA`。表单页最该翻的 `placeholder`（"Enter your name"、"搜索…"）全被跳掉。

**修复**：拆出独立的 `SKIP_TAGS_ATTR`，只跳技术标签，不跳表单控件。

### 2.6 兜底扫描重复收集 —— 产生丢词的垃圾段

**现象**：`<p>See the <a>manual</a> for details.</p>` 会同时产出 `"See the for details."`（丢词）和完整句两条。

**根因**：兜底遍历按"直接文本子节点"扫，把已经整段收集过的 `<p>` 又收了一遍。

**修复**：兜底遍历跳过块级标签（归第一步管）。

### 2.7 选区被浏览器清空 —— 「翻译选中」永远读不到

**现象**：选中文字后点「翻译选中」，永远提示"没读到选中内容"。

**根因（三层）**：
1. 点击侧栏让页面 webview 失焦，浏览器**立刻清空选区**，按钮 handler 再读 `window.getSelection()` 时已经空了；
2. 试过 `WebviewBuilder::initialization_script` 注入缓存脚本 → **没生效**；
3. 又试 `on_page_load` 里 `eval_js_with` 注入 `page_selwatch.js` → **也没生效**。

**修复**：在**读取侧兜底注册**监听器（`page_selection.js` 开头）。它和读 `getSelection` 是同一个执行世界，必然捕获得到选中的 Range。

**代价**：本次调用才装上监听器，所以**第一次点会失败**，此后正常。若要根治，需查清为什么两种注入方式都没生效（可能要在 `add_child` 的 builder 上验证，或改用 WebKit user script 的 `add_script`）。

**诊断字段**：`read_selection` 返回里加了 `selwatch`（监听器是否已挂），排查"选中就丢"时看它。

## 3. 性能：批次大小的实测依据

`live_批大小对单批耗时影响` 实测结果：

| 段数/批 | 单批耗时 |
|---|---|
| 1 | 7.46s |
| 5 | 6.72s |
| 15 | 5.90s |
| 30 | 7.08s |
| **60** | **9.05s** |

**结论**：单批耗时**几乎与批大小无关**，固定开销约 6 秒/批（会话 + SSE + 模型唤醒），推理边际成本只有 ~0.07 秒/段。

所以**批开大 = 直接省时间**：

- 参数从 25 段/2000 字符 → **60 段/6000 字符**
- RFC 9110：257 批 → 约 40 批
- 真机 WIRED 文章：122 段只跑 **4 批、约 2 分钟**

并发的收益有限（实测 6 批并发仅 1.36x），因为本机模型基本串行推理。

另有**视口优先**：收集时标记是否在视口内，当前屏幕的段落排翻译队列最前；配合前端**分批写回**（每批翻完立刻上屏），用户抬眼就看到本屏变中文。

## 5. 遗留问题

1. **「翻译选中」完整链路未最终确认** —— 选区读取已通（`has_selection: true`），但"点完出译文"没验完。
2. **第一次点必失败** —— 兜底注册的代价，体验不佳，值得再攻注入方案。
3. **页面白屏** —— 整页汉化跑动中出现过内容区白屏，未查清是否写回相关。
4. **两个翻译入口并存** —— 翻译面板的旧「翻译当前页面」（Google/Bing，且无还原功能）与 AI 侧栏的「翻译当前页」重复，易混淆。
5. **长段子块跨批** —— 分批写回下子块拼接的边界情况只有单测覆盖。
6. **两种失效的注入方式**（`initialization_script`、`on_page_load`）代码仍在，要么查清原因要么删掉。
