# F-CEF-24 CPU 优化方案（2026-10-27）

## 现象
安装版 release 主进程 CPU 64–85%，debug 100%。

## 根因（perf 栈，已钉死）
```
gtk_main_iteration_do
  → g_main_context_iteration
  → libxcb __libc_recvmsg
  → libcef x11::Connection::HasPendingResponses()
```
CEF 在 GLib 主循环注册的 X11 source 忙轮询，每次 `g_main_context_iteration` 都去 xcb 收消息。

## 实验数据
| 配置 | CPU | 结果 |
|---|---|---|
| `multi_threaded=0` + 固定 10ms 泵 | 100% | 窗口/输入正常 |
| `multi_threaded=0` + 固定 50ms 泵 | 85% | 可用（当前） |
| `multi_threaded=0` + `external_message_pump=1` + `OnSchedule` | 85% | CEF **不调用** OnSchedule（0 次） |
| 注释 `do_message_loop_work` | 104% | 证明不是泵 |
| `multi_threaded=1`（CEF 自跑消息循环） | **5.5%** | 窗口操作跨线程 panic |
| `--renderer-process-limit=3` | 崩溃 | Vulkan/SwiftShader 组合不兼容，已回退 |

## 改造步骤（1-2 天）
1. `CefSettings.multi_threaded_message_loop = 1`（CEF 消息循环独立线程，CPU 5.5%）
2. 把 `SHELL_TABS` / `BROWSERS` / `SHELL_TOOLBAR_VIEW` 从 `thread_local!` 改成全局 `Mutex`/`OnceLock`（跨线程安全）
3. 所有 CEF 调用改为投递到 CEF UI 线程：
   - `cef::post_task(ThreadId::UI, task)` 或 `CefPostTask(TID_UI)`
   - 需要包一层 `cef_ui(|| ...)` 辅助
4. 关键调用点（按优先级）：
   - `force_show`：`window.show()` / `XMapRaised`
   - `apply_toolbar_height`：`view.set_bounds`
   - `run_toolbar_js`：`frame.execute_java_script`
   - `new_tab` / `close_tab` / `switch_tab`
   - `handle_action` 的浏览器操作
5. 回调线程：`on_window_created`/`on_load_start`/下载回调等现在就在 CEF UI 线程，保持
6. 回归：单窗口/输入/关窗退出/证书/用户脚本/下载/书签/设置面板

## 风险
- 投递后异步，按下标操作标签要防越界（投递时校验）
- `force_show` 的 X11 操作可在主线程，CEF `window.show()` 必须投递
- 改全局锁后，注意死锁（回调里再投递/加锁）

## 回退
`multi_threaded_message_loop = 0` + 固定 50ms 泵（当前可用配置），单行回退。
