## 二、架构改造总策略：三层分离

```
┌─────────────────────────────────────────────┐
│  UI 层（Vue）                                │
│  桌面布局 / 移动布局（需分离）                │
├─────────────────────────────────────────────┤
│  业务核心层（跨平台复用 ★）                   │
│  ai/feed/reader/translate/gpc/audit/netmon   │
│  + 开放 API + MCP + 数据层(db/*)             │
├─────────────────────────────────────────────┤
│  引擎适配层（平台相关，需多后端）★核心工作     │
│  webview / 布局 / 下载 / 证书 / 托盘 / 权限    │
└─────────────────────────────────────────────┘
```

**核心工作 = 把「引擎适配层」抽象成 trait，为三平台各写实现。**

## 三、Windows 方案

### 3.1 技术选型
- **引擎**：**WebView2**（Chromium 内核！）——Tauri 2 的 Windows 默认后端
- **优势**：Chromium 内核 → **兼容性比 Linux 版还好**（UA/特性检测问题自动消失）
- **代价**：WebKitGTK 的 API 全部要换 WebView2 等价物

### 3.2 改造清单
| 模块 | Linux 现状 | Windows 实现 |
|---|---|---|
| webview 创建 | `WebviewBuilder` + GTK 容器 | Tauri 原生 WebviewWindow（简化） |
| 布局 | `GtkFixed` 手动定位 | CSS/原生窗口布局 |
| 下载 | `decide-policy` + 信号 | WebView2 下载事件 |
| 证书 | `gio::TlsCertificate` | WebView2 `Certificate` API |
| 托盘 | `ksni`（D-Bus） | Tauri `tray-icon`（跨平台） |
| 快捷键 | GTK 顶层窗口拦截 | Tauri global-shortcut |
| 协议处理器 | `shift://` 手写 | Tauri 自定义协议（原生支持） |
| 权限 | `connect_permission_request` | WebView2 `PermissionRequested` |
| 内容过滤 | 手写 FFI | WebView2 `AddWebResourceRequestedFilter` |

### 3.3 分期
| 期 | 内容 | 预估 |
|---|---|---|
| **W1** | 引擎 trait 抽象 + Windows 骨架编译通过 | 3-5 天 |
| **W2** | webview/布局/下载打通（能浏览网页） | 1 周 |
| **W3** | 证书/托盘/快捷键/权限 | 1 周 |
| **W4** | 数据层/API/MCP 打通 + 打包（NSIS/MSI） | 3-5 天 |

**合计：约 3-4 周**（熟悉 Tauri 2 Windows 的前提下）

## 四、Android 方案

### 4.1 技术选型
- **引擎**：**系统 WebView**（Android 的 Chromium WebView）——Tauri 2 移动端默认
- **优势**：Chromium 内核，兼容性好
- **劣势**：**UI 必须重做**（桌面布局在手机上不可用）

### 4.2 改造清单（比 Windows 多一层 UI 重做）
| 模块 | 处理 |
|---|---|
| 引擎适配 | 同 Windows 思路（Tauri 移动端 API） |
| **UI 布局** | **全部重做**：桌面标签栏/侧栏/分屏 → 移动式（底部导航/抽屉/手势） |
| 快捷键/右键菜单 | 改为**手势/长按** |
| 系统托盘 | Android 无 → 改**前台服务/通知** |
| 扩展体系 | Android WebView 限制多，需评估 |
| 文件系统 | 走 Android SAF/MediaStore |
| 打包 | AAB/APK（Tauri CLI + Android Studio） |

### 4.3 分期
| 期 | 内容 | 预估 |
|---|---|---|
| **A1** | Tauri 2 移动端项目初始化 + 能跑起来 | 3-5 天 |
| **A2** | 引擎适配（能浏览网页） | 1 周 |
| **A3** | **移动 UI 重设计 + 实现**（最大工作量） | 2-3 周 |
| **A4** | 数据层/同步/AI 打通 + 打包 | 1 周 |

**合计：约 5-6 周**（UI 重做是大头）

## 五、关键决策点（需高哥拍板）

### 决策 1：是否做「引擎 trait 抽象」？
- **做**：一次性投入，三端受益，长期正确
- **不做**：各端直接写分支，短期快、长期烂
- **建议**：**做**（这是所有移植的地基）

### 决策 2：产品定位
| 选项 | 说明 |
|---|---|
| **桌面优先** | Windows 做，Android 缓（或不做） |
| **双端并进** | 同时推，资源翻倍 |
| **先 Windows** | 复用度高（UI 基本不变），风险小 |
- **建议**：**先 Windows，再评估 Android**

### 决策 3：Android 的「浏览器」定位
Android 上做浏览器要面对：**系统 WebView 限制、应用商店审核、与 Chrome 竞争**
- 是否值得？**建议先明确场景**（自用？分发？）

## 六、风险清单

| 风险 | 等级 | 应对 |
|---|---|---|
| 引擎 API 差异超预期 | 🔴 高 | 先做**最小可行性验证**（spike）再全面投入 |
| Android UI 重做工作量 | 🔴 高 | 单独排期，勿低估 |
| WebKitGTK 特有能力（内容过滤/证书）无对应 | 🟠 中 | 逐项评估替代或降级 |
| 维护成本三端翻倍 | 🟠 中 | trait 抽象 + CI 三平台构建 |
| Android 分发合规 | 🟡 低 | 先自用，后评估 |

## 七、建议路线图

```
阶段 0（1 周）：引擎 trait 抽象 + Windows spike 验证
    ↓
阶段 1（3-4 周）：Windows 完整实现 + 打包
    ↓
阶段 2（评估）：Android 可行性复核（UI/分发/价值）
    ↓
阶段 3（5-6 周）：Android 实现（若评估通过）
```

**总计：Windows 约 1 个月，Android 再约 1.5 个月。**

## 八、立即可做的（低成本）

1. **CI 加 Windows 构建**（现在只跑 ubuntu）——提前暴露编译问题
2. **引擎 trait 抽象**（阶段 0）——无论做不做移植，都是好架构
3. **前端响应式改造**（渐进）——为移动端铺路，桌面端也无害
