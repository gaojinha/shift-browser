# ShiftBrowser（Tauri）全面系统性分析与升级方案

> 分析基线：`master` @ `f201da9`（v5.7.0），**2026-09-24 已对照 `5290513`（R2-1a/b/c 八个拆分提交之后）复核修订**：量化指标与行号引用已按最新 master 更新
> 分析日期：2026-09-24（首次分析 + 同日复核修订）
> 分析范围：`src/`（Vue 3 前端）+ `src-tauri/`（Rust 后端）+ 构建/CI/安全基础设施
> 代码规模实测（复核后）：Rust 约 **24,950 行**，前端约 **14,110 行**；Rust 测试 **187 个**（`cargo test --lib --list`），前端测试 **2 文件 / 5 用例**。

---

## 一、执行摘要

本项目工程基线**显著高于**同类个人/小团队项目：具备单一事实来源（SSOT）契约生成、纵深安全防御、selfcheck/冒烟/CI/模糊测试/供应链审计一应俱全。

**核心结论**：截至本基线，历史上标识的 **P0 级（确定性正确性/安全缺陷）已全部关闭**——SSRF DNS-pinning、只读闸门写名单漂移、HTTP 读体截断、DB 启动失败静默、panic 无证据、模型网关 SSRF、WebKit 渲染 workaround 均已修复并有测试/护栏。当前矛盾已从"安全/正确性"转向**结构性技术债**，集中在三点：

1. **GTK 手工叠层渲染架构**（`unsafe` FFI reparent + 链接点击 JS 兜底 + 事件手工转发）——一切"焦点/闪烁/点击/遮挡" workaround 的根源，且锁定单窗口、阻挡跨平台与移动端。
2. **巨型单体（部分已处理）**——初始基线时 `api.rs` 膨胀到 **2380 行**、`lib.rs` 2005 行；R2-1a/b/c 拆分提交（`0e5871a`–`5290513`）已把 `lib.rs` 降到 810 行、`api.rs` 降到 257 行装配 + 4 个子模块，但 `api/handlers.rs`（744 行）、`api/http.rs`（953 行）仍超目标，`SettingsDialog.vue` 3175 行、`db/users.rs` 1160 行的"就地堆叠"模式尚待处理。
3. **测试与工程偏科**——后端纯逻辑测试强（187），前端 stores/components 接近零测试（5 用例）；命令错误统一 `Result<_, String>` 不可程序化区分；无自动更新、无 i18n。

后续投资建议：先做"结构债止血 + 测试补课"，再做"渲染层去风险 spike"，最后才是产品化与跨平台。

## 二、项目概览

### 2.1 技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 桌面框架 | Tauri 2.11（`unstable` 多 webview + `custom-protocol`） | 仅 Linux/GTK |
| 渲染引擎 | WebKitGTK 2.52（GTK 3） | GtkOverlay + GtkFixed 多 webview 叠层 |
| 前端 | Vue 3 + TypeScript + Pinia + Tailwind CSS 4 + Vite | 约 45 文件 |
| 数据库 | SQLite（sqlx 0.8 异步连接池，WAL） | 自建迁移系统（15 个迁移，`migrations/`） |
| 加密 | aes-gcm / pbkdf2 / hmac-sha2 | 密码库 + 账号 + 同步 |
| AI 通信 | reqwest（rustls, SSE 流式）· OpenAI 兼容协议 · MCP JSON-RPC 2.0 | 多 Provider + MCP 客户端/服务端 |
| 契约生成 | `build.rs`（常量/契约→TS）+ `ts-rs`（Rust struct→TS） | 单一事实来源 |

### 2.2 架构分层

```
src/                         Vue 3 前端（组件 + Pinia stores + 生成类型）
src-tauri/src/
├── engine/                  引擎抽象层（webview/layout/content/ai_provider/mcp/agent/…）
├── db/                      数据层（bookmarks/history/passwords/vault/sync/settings/…）
├── tabs.rs + tabs/          多 webview 生命周期 + WebKit 信号
├── ai.rs / agent_cmd.rs     AI 对话 + Agent 执行
├── api.rs + api/            开放 API（Unix socket + HTTP 双形态；R2-1c 已拆 api/{handlers,http,auth,dashboard}）
├── capabilities.rs          能力注册表（工具/命令/动作 SSOT）
├── bin/mcp_server.rs        MCP Server 二进制（26 工具）
└── migrations/              SQLite 迁移
```

### 2.3 已具备的工程能力（高基线资产）

- **SSOT 治理**：`constants.rs` / `contracts.rs` / `capabilities.rs` 单一来源，`build.rs` + `ts-rs` 生成前端契约，彻底消灭"注释写'与后端一致'"的人肉同步（治理方案已文档化）。
- **纵深安全**：密码库 AES-256-GCM + PBKDF2 600k + 空闲自动锁定；API token 常量时间比较（`ct_eq`）+ 一次性 dashboard 门票 + 登录指数退避；CIDR 白名单 + IPv4-mapped IPv6 归一化；阅读模式 ammonia 白名单；Agent 动作白名单 + 每步人工确认。
- **完整 CI**：前端 lint/npm audit/类型检查/构建；后端 fmt/check/clippy(-D warnings)/unwrap 护栏/test；`cargo audit` 供应链扫描；每周 cargo-fuzz（HTTP 解析/codec/CIDR 三目标）；Dependabot 覆盖 cargo/npm/actions 三生态。
- **可观测性**：selfcheck 17 项只读体检、tauri-plugin-log 结构化日志、panic hook 落盘 `panic.log`、`scripts/smoke.sh` 10 项 E2E 冒烟。

## 三、现状问题清单

> 分级：**P1**=架构/性能瓶颈（高优先级）· **P2**=代码质量/安全加固（中）· **P3**=体验/可维护性/扩展性（低/规划）。
> 说明：历史上 HANDOFF 标识的 P0 项经复核**均已关闭**，见 3.6 节。

### 3.1 P1 · 架构设计不足

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| P1-1 | **GTK 手工叠层是全部 workaround 根源**：`unsafe gtk_widget_reparent` FFI、GtkFixed 绝对定位、链接点击靠注入 JS 兜底、button/scroll 事件逐一手工转发、弹窗必须隐藏所有网页 webview | `tabs.rs:488-491`（`gtk::ffi::gtk_widget_reparent` FFI）、`:528`（`elementFromPoint` 兜底 JS）、`:774/806`（set_focus 焦点转发）、`:523/553`（grab_focus 强制聚焦） | 焦点/输入/闪烁/黑角反复复发；Wayland/X11 分叉；窗口形态改动成本极高；是跨平台/多窗口的硬阻塞 |
| P1-2 | **引擎抽象未闭合**：trait 已建但业务层仍有 15 处直接 `use webkit2gtk/gtk`（较历史 130 处已大幅收敛，但未清零） | `grep 'use webkit2gtk|use gtk'`（排除 engine/）命中 15 | 非 Linux 只有 `unsupported` 桩，Windows/Android 移植无法启动 |
| P1-3 | **全局静态可变状态 39 处**（UI_FOCUSED / LOCKED / UNLOCKED / DEVTOOLS_ENABLED / TRANSLATE_RATE …） | `grep '^static \|pub static '` 命中 39（复核后） | 锁定单窗口、隐式耦合、难单测 |
| P1-4 | **启动关键路径串行 `block_on` 7 次**（DB、锁屏设置、verify_password、clear_session、userscripts 缓存、settings 预热、allowlist/UA/strict） | 启动装配已随 R2-1b 移入 `app/bootstrap.rs`（含 7 处 `block_on`，原 lib.rs 行号失效） | 冷启动白屏长；任一依赖卡住整个启动挂起 |

### 3.2 P1 · 性能瓶颈

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| P1-5 | **内存随标签数线性膨胀**：每标签独立渲染进程（据项目记录约 240–500MB/进程，实测 9 标签 3.75GB），空闲仅按固定时间（~30 分钟）休眠，不看内存水位 | `HANDOFF-2026-09-24` P1-2；tabs 休眠逻辑 | 10+ 标签即进入 swap；无 `/proc/meminfo` 水位驱动的主动回收 |
| P1-6 | **会话恢复串行**：N 标签 = N 次顺序 IPC + N 个 webview 创建 | `stores/tabs.ts` 会话恢复路径 | 恢复 20 标签明显卡顿 |

### 3.3 P2 · 安全隐患（残余）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| P2-1 | **CSP 开发模式含 `unsafe-inline`/`unsafe-eval`**（生产 CSP 已收紧为 `script-src 'self'`，`withGlobalTauri: false` 已正确） | `tauri.conf.json:31`（dev） | 仅 dev 生效，攻击面可控，但易被误用 perf 到生产 |

## 四、升级方案

> 估算基准：1 名熟悉 Rust + Vue 的全职工程师；2 人并行约压缩 40%。

### R1 · 结构债止血（第 1–2 周）

> **2026-09-24 复核**：R1 第 1 条（api.rs 拆分）**已实际完成约 80%**——`R2-1a/b/c` 八个提交（`0e5871a`–`5290513`）已把 `api.rs` 2380→257 行装配 + `api/{handlers.rs 744, http.rs 953, auth.rs 277, dashboard.rs 209}`；剩余差距：`handlers.rs`/`http.rs` 未拆到 <400 行、命令分发仍是单体 match 未改注册表。第 2 条（`AppError`）与第 3 条（前端测试）未动。
> 原 R1 周期估计 1–2 周按当前进度**剩余约 1 周**（handlers/http 二次拆分 + 注册表）+ 2 条未动项各 3–4 人日。

**目标**：把当前最大的可维护性风险（`api.rs` 单文件 2380 行 + 命令错误 `String` + 前端零测试）先控制住，为后续重构铺路。

1. **`api.rs` 拆分**（技术选型：模块化重构，暂不引入 HTTP 框架）
   - 拆为 `api/{socket.rs, http.rs, auth.rs, gateway.rs, commands.rs, mod.rs}`；
   - 30 命令分发从单体 `match` 改为 `(cmd, handler)` 注册表（与 `capabilities::ids()` 同源，保留防漂移测试）；
   - 目标：单文件 <400 行，`api.rs` 只留装配。
2. **错误类型化**（技术选型：`thiserror`，已在依赖中）
   - 定义 `AppError` 枚举 + 错误码（如 `E_DB` / `E_PERM` / `E_TIMEOUT` / `E_AUTH`）；
   - 命令边界 `Result<T, AppError>`，经 `impl Serialize` 输出 `{code, message}`；
   - 前端 `invoke` 封装按 `code` 分支处理（重试/降级/用户提示）。
3. **前端测试补课（关键路径）**
   - `stores/tabs.ts`（切换/关闭/休眠语义）、`settings.ts`（默认值/白名单）、`ai.ts`（流式回退）各补关键路径用例，覆盖 ≥60%；
   - 复用 `vitest` + `vi.mock("@tauri-apps/api/core")` 既有模式。

**实施步骤**：① `api.rs` 拆分与注册表（**已完成 80%，余 handlers/http 二次拆分 + 注册表**，跑 `cargo test` 保绿）→ ② 引 `AppError` 逐步替换 36+ 签名 → ③ 补前端测试并行进行。
**资源**：剩余约 1 人 8 人日（已完成 2 人日）。
**风险**：拆分可能引入行为回归 → 用既有 187 测试 + smoke.sh 回放 + 对 API 请求-响应录制比对。
**验收**：`api/` 子模块全部 <400 行；`cargo test`/clippy/-D warnings 全绿；前端关键路径覆盖 ≥60%；API 全部命令回放结果一致。

### R2 · 渲染层去风险（第 3–6 周）

**目标**：消除最深的架构债——`unsafe` reparent 及一系列事件/点击/遮挡 workaround。这是后续一切（多窗口/跨平台/移动）的前置。

1. **受控 spike（第 3 周，只读研究，不动主线）**
   - 量化五维：焦点/输入、闪烁、链接点击、弹窗遮挡、滚动，在多 webview（现状）与候选方案下的表现；
   - 产出一份可决策的技术报告（成本/收益/风险表）。
2. **二选一（第 4–6 周落地）**
   - **方案 A（推荐）**：保留多 webview，将网页 webview 改由原生 Tauri `WebviewWindow`/容器布局承载，替代 `GtkFixed + gtk_widget_reparent`（消除 unsafe FFI 与焦点/遮挡 workaround）；内存按 `/proc/meminfo` 水位主动休眠替代固定 30 分钟。
   - **方案 B（对照）**：单 webview 多标签（Chrome 风格，工程量最大，仅作对照）。
3. **回归护栏同步增强**：`scripts/smoke.sh` 从 10 项扩到 20 项，新增"链接点击/弹窗/滚动"断言式检查。

**资源**：1 人 4 周（spike 1 周 + 落地 3 周）；方案 B 另需 6 周，不建议首发。
**风险（高）**：历史高发区（焦点/链接）易回归。对策：spike 通过才动，特性开关可回退，失败即回滚。
**验收**：删除 `gtk_widget_reparent` 及 `elementFromPoint` 兜底 JS；10 标签稳态 RSS **-30%**；smoke 20 项全过；真人双周验收焦点/链接/弹窗无回归。

### R3 · 启动与内存治理（第 7–9 周）

1. **启动并发化**：合并 `lib.rs` 7+ 处串行 `block_on`，可并行项（userscripts 缓存/settings 预热/allowlist/UA）用 `futures::join!` 一次性 await。
2. **内存水位休眠**：新增 `/proc/meminfo` 监控，可用内存低于阈值时按 LRU 主动休眠非活动标签（替代只看时间的策略）。
3. **状态收敛**：全局 `static`（UI_FOCUSED/LOCKED/DEVTOOLS_ENABLED 等）归入统一 `AppServices`（`OnceLock` + 内部结构体），显式读写接口，为多窗口打底。
4. **大会话恢复**：恢复改为一次批量后端命令 + 非活动标签延迟加载。

**资源**：1 人 3 周。
**验收**：冷启动到首标签可交互 **-40%**；恢复 20 标签 **-60%**；全局 static 从 35 降至个位数（集中管理）。
