# ShiftBrowser 网站兼容性测试方案

用浏览器自身开放 API 驱动真实 WebKit 内核批量访问主流网站，验证加载→读取全链路。
本轮实测报告见 `site-compat-test.md`（15/15 通过）。

## 一、测试原理

不借助外部工具（curl/Selenium），直接调浏览器本地 HTTP API 的 `open_and_read` 命令。
该命令走完整业务链路：开新 AI 标签 → 等 SPA 渲染稳定 → 入口 SSRF 校验 → 最终 URL
复核 → 可达验证 → 读取 DOM 正文 → 关闭标签。任一环节失败都会在返回中体现，
因此单命令即可覆盖"能不能开、能不能读"。

- 地址：`POST http://127.0.0.1:19701/api`
- 鉴权：`Authorization: Bearer $(cat ~/.local/share/com.shiftbrowser.app/api-token)`
- 参数：`{"cmd":"open_and_read", "url":"…", "close":true, "max_chars":500}`
- 通过标准：返回 `ok=true` 且 `data.read_ok=true`

## 二、网站清单选型

覆盖 8 大类型，每类至少 1 个，优先选 JS 重、反爬严、有代表性的站：

| 类型 | 网站 | 选型理由 |
|------|------|----------|
| 搜索 | 百度、必应 | 入口站，SPA 程度低，基准对照 |
| 代码 | GitHub、Gitee | 大型 React 应用，scheduler 兼容试金石 |
| 视频 | B站 | 视频+信息流，wheel 劫持与 412 风控观察点 |
| 社交 | 知乎、微博、豆瓣 | 登录墙、反爬、懒加载各异 |
| 电商 | 淘宝、京东 | 重 JS、首屏文本少，渲染等待压力测试 |
| 新闻 | 网易、澎湃 | 传统门户 vs 现代前端 |
| 技术 | 掘金、CSDN | 技术博客结构，阅读模式对照 |
| 文档 | MDN | 纯文档站，加载速度基准（最快） |

## 三、执行步骤

1. 确认浏览器已启动：`curl … '{"cmd":"status"}'` 返回 `ok=true`
2. 跑批量脚本：`./scripts/site-compat-test.sh`（单站超时 60s，全量约 4 分钟）
3. 记录每站 `ok/read_ok/耗时/错误` 四项
4. 失败站单独复测一次（排除偶发网络波动），仍失败则按第五节定位

## 四、结果判定

- `ok=true read_ok=true`：通过
- `ok=false`：按 `error` 字段归因——SSRF 拦截类看是误伤还是真风险；
  可达验证失败看复测是否恢复（CDN 波动偶发）；风控类（412）记已知限制
- 耗时 > 30s：记性能观察项（SPA 渲染等待久或站点慢）

## 五、失败定位手册（本轮沉淀）

1. 先手动单测该站，确认是必现还是偶发
2. 偶发 + CDN 大站 → 倾向网络波动，复测
3. 必现 + `重定向复核拦截` → 查是否真跳内网
4. 必现 + `可达验证失败` → 先复测，连续失败再查 DNS/代理
5. 页面打不开 + 无响应 → 关 `compat_chrome_fp` 二分指纹脚本，
   再把域名加隐私白名单二分 privacy.js（GitHub ANR 即此法定因）
6. 滚轮失灵 → 开 `SHIFT_SCROLL_DEBUG=1` 对比 fixed/child 事件层

## 六、回归要求

发版前跑一遍全量；改动 SSRF/注入/UA/滚动相关代码后，必跑全量 + 复查本文档
第五节相关项。新增网站类型时同步更新清单与脚本。
