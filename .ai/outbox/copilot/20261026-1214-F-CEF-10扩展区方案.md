## 先说关键结论
主应用的「扩展」**不是 Chrome 扩展**，是「用户脚本/样式注入」：只读 manifest 的 `content_scripts` 的 js/css，不支持 `action`/popup/background。Chrome 式「图标 + popup」在数据层面没有对应物，只能做简化版。

## 1. 数据从哪来
- 表（`src-tauri/migrations/20260905000000_init.sql:108`）：`extensions(id, name, path, enabled DEFAULT 1, created_at)`，仅 5 列。
- 已启用查询：`SELECT id,name,path FROM extensions WHERE enabled=1`；现成封装 `db/extensions.rs::list` 返回全部，需自行滤 enabled。
- `ExtensionInfo`（`extensions/manager.rs:11`）的 version/description/js_count/css_count **不在表里**，是 `list_extensions` 每次现读 `path/manifest.json` 得到。
- 本机 `shift-browser.db` 的 extensions 表实查**无行**（脚本无输出），故没有真实样本，以下来自代码而非实测扩展。

## 2. CEF 下能不能用
- `ExtensionInfo` **没有** `manifest`/`icons` 字段（派单假设不成立）。manager.rs 的 `Manifest` 只反序列化 name/version/description/content_scripts；extensions/ 下搜 icons/action/popup 无命中。
- 图标：主应用**不缓存**。`path` 是用户加载时的原目录（`load_extension` 直接存入参），图标需自己读 `<path>/manifest.json` 的 `icons` 再读文件（需新增解析）。
- 安全：读图标必须沿用 manager.rs 的双防线（拒 `..` + canonicalize 后仍在扩展目录内），建议抽公共函数，不要复制第三份。
- **更大的缺口**：`inject_extensions` 用 `app.get_window("main")` + `window.webviews()`（Tauri 窗口），CEF 独立窗口里没有这些 webview，扩展脚本在 CEF 下**目前不注入**。图标显示了也是摆设，需另立卡（可复用 F-CEF-03 的 `browser::inject_marker` 通道）。

## 3. UI 放哪 / 宽度
- 现状：`.bar` 48px 高，flex，gap 2px，padding 0 8px；按钮 28×28；`.addr-wrap` 为 `flex:1; min-width:0; margin:0 4px`。窗口按钮在**上方标签栏**右侧（`.win-ctrl`），不在地址栏行，所以位置是 `.addr-wrap` 之后、`.bar` 行尾。
- 宽度：每图标 28+2=30px；3 个 90px，5 个 150px；拼图入口再 +30px。1280 宽窗口下地址栏被压 90–180px（约 7–14%）。建议最多直显 3 个，其余进拼图菜单；0 个启用时不渲染（零占位）。

## 4. 点击行为（两方案）
- **A. 工具栏页内 DOM 下拉 / 新标签**：沿用现有 `new_tab(url)`（shell.rs:694）和 `act` 命令通道；零新增视图。
- **B. 弹层 BrowserView**：仿 Chrome popup，需新浮层 View、定位、失焦关闭，并处理 add_child_view 命中顺序（WORKBOARD 已记工具栏点击穿透隐患，浮层同类风险）。成本约 A 的 4–5 倍（经验估，无实测）。
- 主应用扩展**没有 popup 页**，B 无内容可弹。推荐 A：点图标 = 下拉菜单列出扩展，可切换启用/禁用。
