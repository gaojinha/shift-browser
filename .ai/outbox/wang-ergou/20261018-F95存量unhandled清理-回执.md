### 二、根因（同一类）

测试把 `invoke` / `invokeOk` 的**默认实现**写成 `Promise.resolve(undefined)`，
而 store / 组件是把返回值**直接**写进数组字段的：

```ts
// stores/bookmarks.ts:22
this.bookmarks = await invoke<Bookmark[]>('get_bookmarks')   // ← undefined 直接落库
```

于是渲染 / 计算属性读 `.length`/`.filter`/`.map` 时崩。因为崩在 `flushJobs`
的微任务里（渲染 effect），测试本体已经跑完，所以表现为「事后冒出的 unhandled」。

### 三、修法（只动测试文件）

产品代码不动——store 信任 `invoke<T>` 的类型是既有约定，改产品会破坏「同一类判定只许一份实现」。

`App.test.ts`：抽出 `baseInvoke(cmd)`
- 列表类命令 → 空数组：`get_bookmarks` / `get_bookmark_folders` / `get_workspaces` / `get_tabs` / `get_all_settings` / `get_tab_groups` / `get_recent_history`
- `create_tab` → 合法 Tab 对象；`get_newtab_url` → 字符串；`get_split_tab` / `load_last_session` → `null`
- `vertical_tabs` 那条用例的自定义 mock 改为「只覆盖 `get_all_settings`，其余回落 `baseInvoke`」

`McpSection.test.ts`：该 6 例**已由 atomcode `f56c8a3`（F-86 补遗）先行修掉**
（`mockResolvedValue(undefined)` 改 `mockImplementationOnce`，重拉列表回落默认实现），
二狗核对后**未重复修改**，只把 F-95 卡的责任范围据实收窄。
