## F-23 perms.rs 单测补课 — 交付回执

**结论：perms.rs 从 0 测试补到 8 条；补测前先抽边界，顺带修掉 2 处脆性 + 2 处瑕疵。提交 `e6058d3`。关口全绿。**

### 一、为什么要先重构才补测
perms.rs 281 行、安全敏感（摄像头/麦克风/地理位置/通知的放行白名单），却**零测试**。

### 二、动出的 2 处脆性（重复解释 / 自造自解）
1. **`"kind|host"` 往返编码**：内存缓存 `HashSet<String>`，键是拼出来的
   `format!("{}|{}", kind, host)`；`list_permission_rules` 又 `splitn(2,'|')` 拆回来。
   等于自己造格式、自己解格式。→ 改 `HashSet<(String, String)>` 元组，列表直接映射，不再拆串。
2. **「读 settings→解 JSON→合并→写回」抄了三遍**（`respond_permission` /
   `remove_permission_rule` / `load_allowlist`）。→ 收成单一写入口：
   `read_allow_map` / `write_allow_map` / `merge_rule`（纯函数）/ `apply_rule`。

### 三、修掉的 2 处瑕疵（真 bug 苗子）
1. **撤权静默失效**：`remove_permission_rule` 原用
   `UPDATE settings SET value=? WHERE key='perm_allow'`——**行不存在时啥也不干也不报错**。
   → 统一走 upsert（`INSERT … ON CONFLICT DO UPDATE`），不依赖调用方先建行。
2. **撤权留空壳**：撤销最后一条授权后，库里留下 `{"media": []}`。虽然 `load_allowlist`
   能容忍，但脏。→ `merge_rule` 在列表清空时整条 kind 剔除。
