## 0. 结论先行（给二狗的最关键 5 条）

1. **改造的实质不是「加锁」，而是「把所有 CEF 句柄操作从『单线程巧合』变成『显式投递到 CEF UI 线程』」。** 现状 `thread_local` 能安全，全靠 `multi_threaded_message_loop=0` 时 CEF 回调与 `run_on_main_thread`/glib 定时器**恰好都跑在 GTK 主线程一条线程**上。`multi_threaded_message_loop=1` 后 CEF 回调迁到 CEF 自己的 UI 线程，`run_on_main_thread`/glib 定时器仍在 GTK 主线程——**同一批 `thread_local` 被两条线程各读各写一份独立存储**，静默丢数据（不是报错），表现会是「窗口没创建 / BROWSERS 查不到 / 标签栏不刷新」。这是方案表里 `multi_threaded=1 → 窗口操作跨线程 panic` 的真正根因。

2. **cef-rs 句柄类型（Window/View/Browser/Client/BoxLayout/Frame/Task）全部已 `Send+Sync`**（`cef` crate `src/rc.rs:283-284` 的 `unsafe impl<T: Rc> Send/Sync for RefGuard<T>`）。所以**句柄可以直接放进共享 `Mutex`，不需要任何额外 `unsafe impl`、不需要把句柄留在线程内**。这比方案文档设想的省事——`SHELL_WINDOW: RefCell<Option<Window>>` 直接换 `Mutex<Option<Window>>` 就能编过。但注意：**`Send+Sync` 只保证「句柄能跨线程移动/共享」，不保证「能从任意线程调它的方法」**——CEF 仍要求所有句柄方法调用在 CEF UI 线程。锁管存储、`cef_ui` 管调用，两者缺一不可。

3. **`cef_ui` 辅助必须带 `currently_on(ThreadId::UI)` 短路**（已在 crate 确认存在 `cef::currently_on`，`bindings/x86_64…:57919`）：若已在 CEF UI 线程就**原地执行**、不投递。没有这条，任何 CEF 回调里调 `cef_ui_call`（投递后阻塞等结果）会 post 给自己 → 自己的循环被自己阻塞 → **必死锁**。这是本项目 CEF 回调（on_window_created / on_after_created / on_load_start / 下载回调）都会经 `handle_action` 触发 UI 操作的现实场景。

4. **同步等待（open 拿 tab_id / cef_open_window 等结果）用 `mpsc::channel` 一次性回传，不用 `block_on` CEF 回调**。链路是 tokio →（recv）→ GTK 主线程 →（recv）→ CEF UI 线程执行短任务后回发，**三段各自不同线程、无环**。唯一铁律：**CEF UI 线程上跑的任务里绝不能再 `cef_ui_call` 阻塞等**（由第 3 条的 currently_on 短路天然保证），也绝不能再回头阻塞等 GTK 主线程/tokio。

5. **`RefCell → Mutex` 后，「二次借用 panic」这一类错误消失，换成「持锁进 CEF / 锁内 post_task」这一类死锁风险**。现状没有一处真正嵌套 `borrow`（都是顺序的多个 `.with`，每个闭包结束即还），所以换 `Mutex` 不会新增借用错误；要新增的纪律是**「锁里只 clone 出句柄/数据就放锁，CEF 调用一律在放锁后、且 `cef_ui` 内做」**，绝不在持锁期间调 CEF 或再 `post_task`。

## 1. 线程模型：现状 vs 改造后（为什么 thread_local 会失效）

### 1.1 现状（`multi_threaded_message_loop=0`，`app.rs:83`）

CEF 的回调（`on_window_created`/`on_after_created`/`on_before_close`/`on_load_start`/下载回调）全部由 `cef::do_message_loop_work()` 触发（`app.rs:120`），而 `do_message_loop_work` 只在一个 glib 50ms 定时器里被调（`cef_cmd.rs:129-132`，`gtk::glib::timeout_add_local`）。glib `*_local` 定时器、GTK 信号（`connect_size_allocate`/`connect_delete_event`）、`run_on_main_thread` 的闭包，**都跑在 GTK 主循环那条线程**。所以：

> **现状：所有动 `thread_local` 的代码都收敛在一条线程（GTK 主线程）。** 这就是 `thread_local` 今天安全的全部原因——不是设计如此，是单线程巧合。

### 1.2 改造后（`multi_threaded_message_loop=1`）

CEF 自己起 UI 线程跑消息循环，回调（on_*）全部迁到 **CEF UI 线程**。而 `run_on_main_thread` 闭包、glib `*_local` 定时器、GTK 信号仍在 **GTK 主线程**。于是同一批 `thread_local`：

| 线程 | 会碰哪些 thread_local（举例） |
|---|---|
| **CEF UI 线程**（回调） | on_window_created 写 `SHELL_WINDOW`/`SHELL_LAYOUT`/`SHELL_TOOLBAR_VIEW`（`shell.rs:754/774/810`）；on_after_created 写 `BROWSERS`（`shell.rs:938`）；`handle_action`/`handle_shortcut`（CEF 回调，`shell.rs:2131/3041`）读写 `SHELL_TABS`/`ACTIVE_TAB`/`TAB_SEQ`/`ZOOM_LEVELS`/`LAST_FIND_TEXT`/`BOOKMARKS`/`CLOSED_URLS`/`TAB_CLOSING` |
| **GTK 主线程**（run_on_main_thread + glib 定时器 + GTK 信号） | `force_show` 读 `SHELL_WINDOW`（`shell.rs:469`）；glib 定时器 `refresh_tabbar`/`refresh_bookmarks_ui`（`cef_cmd.rs:430-434`、`shell.rs:552-558`）读 `SHELL_TABS`/`BOOKMARKS`；`set_bookmarks` 写 `BOOKMARKS`（`shell.rs:1670`，来自 `cef_cmd.rs:170` 的 `async_runtime::spawn`，其实是 tokio 线程）；`connect_size_allocate`/`connect_delete_event` 读写 `BROWSERS`（`cef_cmd.rs:286/300/315`）；`cef_navigate`/`cef_close_window` 读写 `BROWSERS`（`cef_cmd.rs:456/472`） |

→ **同一 `thread_local` 被 ≥2 条线程各自持有独立副本**。例如 on_after_created 在 CEF UI 线程把 browser 塞进 `BROWSERS`，而 `cef_navigate` 在 GTK 主线程读 `BROWSERS`——读到的永远是空（两个线程各有一份 HashMap）。这就是表里 `multi_threaded=1` 那行「窗口操作跨线程 panic」的底层机制（句柄空 / 跨线程误用 → CEF assert）。

### 1.3 改造要达到的不变量

把上面两张表里**所有 CEF 句柄方法调用**统一收敛到 **CEF UI 线程**执行（用 `cef_ui` 投递），把**纯数据共享**（标签元数据 / active 索引 / 计数 / 标志 / URL / 书签）换成跨线程类型（`Mutex`/`Atomic*`）。这样两条线程都合规：CEF UI 线程负责「调句柄方法」，GTK 主线程只负责「读纯数据 + 触发投递」。

### 2.4 特殊 case：ACTIVE_TAB / TAB_SEQ / TAB_CLOSING 的 `Cell` 怎么改

`Cell` 不可跨线程，必须换。逐个：

- **`TAB_SEQ`（单调自增 id）** → `AtomicUsize`，`fetch_add(1, Relaxed)`。最干净，无一致性问题。
- **`TAB_CLOSING`（跨线程标志）** → `AtomicBool`。set/reset/读分属 CEF UI / GTK 主 / CEF UI 三条线，必须 Atomic。
- **`ACTIVE_TAB`（与 vec 长度强耦合）** → **推荐并入 SHELL_TABS 同一把锁**，即把两个静态合成一个结构：
  ```rust
  // 伪码：把 SHELL_TABS + ACTIVE_TAB 合成一个受同一 Mutex 保护的单元
  struct TabState { tabs: Vec<ShellTab>, active: usize }
  static SHELL_TABS: Mutex<TabState> = …;
  ```
  理由：`close_tab`（1610 读 len → 1635 remove → 1662 set new_idx）和 `switch_tab`（1543 读 len → 1568 set）都是「先读 vec 长度、再改 vec、再改 active」的复合操作；若 active 用独立 `AtomicUsize`、vec 用独立 `Mutex`，两把锁之间会出现 active 指向已删下标的瞬态（越界，`SHELL_TABS.get(active)` 返回 None 走降级，但语义错）。合成一个 `Mutex<TabState>` 后，len/tabs/active 三者天然原子一致。**这是二狗实编时最省心的选法。**
  - 若坚持 active 独立：用 `AtomicUsize`，且**每次改 vec 后、在读 active 前**都要在锁内校验 `active < tabs.len()`（现有 `get(idx)` 的越界防护 1544/1611 已覆盖，保持即可），并加单测钉住「close 后 active 不越界」。

### 2.5 下载路径旁证（非 thread_local，但同卡相关）

`TRACKS: OnceLock<Mutex<HashMap<u32,DlTrack>>>`（`shell.rs:3205-3208`）**已经是** `OnceLock<Mutex<…>>` 跨线程范式，下载回调（on_before_download 3466 / on_download_updated 3496，CEF UI）与 `downloads_panel_json`（经 cef_cmd.rs:391 的 block_on，GTK 主）共用——**无需改动**，但它正是本卡要把其余 17 个 thread_local 迁向的目标范式，可作参照模板。

> **可编译性已静态验证**：换 `Mutex<…>` 后每个 `static` 要求内层 `Send`（`static` 的隐式约束）。逐一对过——`Window`/`View`/`Browser`/`Client`/`BoxLayout`/`Frame`/`Task` 都是 `RefGuard<…>`（`rc.rs:283-284` 已 `Send+Sync`），`ShellTab{id: String, view: View, title, url}` 因此 `Send`，合成的 `TabState{tabs: Vec<ShellTab>, active: usize}` 也 `Send`。所以**所有 `Mutex<…>` 静态都合法、无需 `unsafe impl`**。

## 4. 交付项③：post_task(TID_UI) 同步等待模式

### 4.1 crate API 已确认（读源码，非猜测）

`cef` crate 154.5.0 在 crate 根 `pub use bindings::*`（`lib.rs:29`），以下直接 `cef::…` 可达（与现有 `cef::CefString`/`cef::initialize`/`cef::do_message_loop_work` 同一口径）：

| API | 签名（bindings/x86_64…） | 用途 |
|---|---|---|
| `cef::post_task` | `fn post_task(ThreadId, Option<&mut Task>) -> c_int`（:57902） | 投递任务到指定线程 |
| `cef::ThreadId::UI` | `pub const UI: Self = Self(TID_UI)`（:47553） | 目标 = CEF UI 线程 |
| `cef::currently_on` | `fn currently_on(ThreadId) -> c_int`（:57919） | **判断当前是否已在某线程**（cef_ui 短路的依据） |
| `cef::task_runner_get_for_thread` | `fn (…) -> Option<TaskRunner>`（:57890） | 备选：拿 TaskRunner 再 post |
| `cef::Task` | `pub struct Task(RefGuard<_cef_task_t>)`（:29512）＋ `wrap_task!` 宏（:29539 有 doctest） | 任务本体；`ImplTask: Clone+Sized+Rc`（:29531），方法 `execute` |
| `cef::do_message_loop_work` / `run_message_loop` | （:58377/:58384） | 现固定泵用的就是前者；multi_threaded=1 后**不再调** do_message_loop_work（CEF 自跑） |

### 4.2 推荐的 `cef_ui` / `cef_ui_call` 两个辅助（二狗可直接落地）

**`cef_ui`（fire-and-forget，绝大多数场景）**：
```rust
// 伪码：把闭包安全投递到 CEF UI 线程；已在 CEF UI 则原地执行
pub fn cef_ui(f: impl FnOnce() + Send + 'static) {
    if cef::currently_on(cef::ThreadId::UI) == 1 {
        f();                       // 关键短路：CEF 回调里调 cef_ui 不会 post 给自己
        return;
    }
    let mut task = UiTask::new(f); // wrap_task! 定义，execute 里跑 f
    cef::post_task(cef::ThreadId::UI, Some(&mut task));
}
```
`UiTask` 用 `wrap_task!` 定义，`execute(&self)` 里 `self.f()`（因 Task 是 RC 包装、execute 是 `&self`，`f` 存 `RefCell<Option<…>>` 或用 `Box<dyn Fn()>`，execute 只跑一次）。**这条短路是整个方案不死的命门**（见第 5 节）。

**`cef_ui_call`（需要同步拿结果：open 拿 tab_id / create_browser 拿 bool / 个别等结果）**：
```rust
// 伪码：投递到 CEF UI 执行并同步拿返回值；已在 CEF UI 则原地执行不阻塞
pub fn cef_ui_call<R: Send + 'static>(f: impl FnOnce() -> R + Send + 'static) -> R {
    if cef::currently_on(cef::ThreadId::UI) == 1 {
        return f();                // 在 CEF UI 上：原地跑，绝不 post+recv（否则 post 给自己→死锁）
    }
    let (tx, rx) = std::sync::mpsc::channel::<R>();
    let mut task = UiTask::new(move || { let r = f(); let _ = tx.send(r); });
    cef::post_task(cef::ThreadId::UI, Some(&mut task));
    rx.recv().expect("CEF UI 线程无响应（任务未执行或 panic）")
}
```
**不用 `block_on` CEF 回调**：调用方（GTK 主线程）阻塞在 `rx.recv()`，CEF UI 线程独立跑任务后 `tx.send`，三段各自不同线程、无环（见 5.2）。

### 4.3 「投递后等结果」用在哪、不用在哪

- **要同步等**（用 `cef_ui_call`）：`open`（要 `Result`）、`create_browser`（要 `bool`）、`cef_open_window`（要 tab_id）。这些调用方都在 GTK 主线程（经 `run_on_main_thread`），**不是 CEF UI 线程**，所以 `cef_ui_call` 的 recv 阻塞是安全的。
- **不用等**（用 `cef_ui`）：`navigate`/`close_tab`/`switch_tab`/`run_toolbar_js`/`refresh_tabbar`/`window_*`/`apply_*`/`do_find` 等——都是「发出去就好」，工具栏靠后续 CEF 回调（load/标题）自己刷新，不需要 Rust 侧等返回值。
- **`run_toolbar_js` 是 fire-and-forget**（execute_java_script 的 CefString 结果被忽略），不是等结果型；方案里点名的「特别注意 run_toolbar_js」——**结论：无需同步等待，`cef_ui` 即可**。

### 4.4 单测钩子（可脱离真机 CEF 测的部分）

把「投递」抽象成可注入的 executor（`trait UiExecutor { fn post(&self, f: Box<dyn FnOnce()+Send>) }`），真机用 `CefUiExecutor`（调 post_task），单测用 `InlineExecutor`（直接跑）。这样可单测：
- **cef_ui 的 currently_on 短路分支**：stub `currently_on==1` → 断言原地执行、不 post。
- **cef_ui_call 的 mpsc 回传**：InlineExecutor 下断言返回值正确送达。
- **post 幂等 / 不重入**：同一 executor 连续 post 两个任务，断言都执行且顺序不变。
（真正的 `post_task` 到真 CEF UI 线程的行为只能在真机验，归二狗。）

## 5. 交付项④：死锁排查（锁序 + RefCell→Mutex 语义变化）

### 5.1 锁序全景（改造后）

改造后只有**一条合法的锁→投递方向**，其余全是坑：

```
[合法] 无锁  --cef_ui/cef_ui_call-->  post 到 CEF UI 线程  -->  CEF UI 任务里[重新]拿锁
[合法] CEF 回调(已在 CEF UI)  --cef_ui 短路--> 原地执行  -->  拿锁
```

把「拿锁」和「post_task/recv」的相对位置画出来，**只有两种死锁拓扑，都要避**：

**坑① 持锁期间 post_task + 被投任务要拿同一把锁（自死锁/互锁）**
```
线程 X 持有 Mutex<TAB_STATE>
  → cef_ui_call { f 里也要 lock TAB_STATE }
  → X 阻塞在 rx.recv()（仍持锁）
  → CEF UI 跑 f，f 里 lock TAB_STATE → 等 X 放锁
  → X 等 CEF UI、CEF UI 等 X 的锁  ==  死锁
```
- 触发面：**任何「持着某状态锁、又调 `cef_ui_call`（或 `cef_ui` 且被投闭包回拿同一把锁）」的写法**。
- 现状对照：`switch_tab`（1548-1567 一个 `.with` 内 `borrow_mut` 改完才结束）→ 1575 又一个 `.with`（BROWSERS）——是**顺序锁**，第一个闭包结束已还锁，没有嵌套，现状安全。换 Mutex 后**只要保持「每个 lock 作用域小、clone 出来就放」**就不会踩坑①。
- **纪律（写进代码注释）**：所有状态锁的 guard 作用域**必须在使用完/clone 完当行内结束**；`cef_ui`/`cef_ui_call` 一律放在**所有状态锁 guard 已 drop 之后**；被投递闭包内**重新独立 lock**，绝不从外层捕获 guard。

**坑② 在 CEF UI 线程上调 `cef_ui_call`（不短路）→ post 给自己**
```
CEF UI 线程跑某任务
  → cef_ui_call { f }  （若没有 currently_on 短路）
  → post_task(TID_UI, f)  投给自己
  → 自己阻塞在 rx.recv()，循环被自己卡住
  → 自己被 post 的 f 永远没机会跑  ==  死锁
```
- **唯一解就是 4.2 的 `currently_on(ThreadId::UI)==1 → 原地 f()` 短路**。两个辅助（`cef_ui`/`cef_ui_call`）都必须带这条，缺一条就会在「CEF 回调链里调 `handle_action` → 又调 `cef_ui_call`」时炸。
- 现实触发链：`on_download_updated`（CEF UI）→ 若它经 `handle_action` 触发某面板 `cef_ui_call` 等结果 → 没短路必死。所以**短路不是优化，是正确性前提**。

### 5.2 同步等待链路（三段无环，已核）

`cef_open_shell`（cef_cmd.rs:441，tokio）→ `run_on_main_thread{ open_shell_on_main }` + `recv()`
→ `open_shell_on_main`（GTK 主）→ `cef_ui_call{ open }` + `recv()`
→ CEF UI 跑 `open` → `tx.send` → GTK 主内层 recv 返回 → 继续 force_show/注册定时器 → 外层 send → tokio 返回。

三段各自不同线程、**无回边**（CEF UI 的 open 不回头等 GTK 主/tokio），所以无环。唯一要守的：`open`/`force_show` 体里**不得再 `cef_ui_call` 阻塞**（它们内部若需动 CEF，用 `cef_ui` fire-and-forget，或已在 CEF UI 就原地）。现状 `open` 只 `browser_view_create`＋登记，无阻塞调用，`force_show` 只 `window.show()`＋X11，均满足。

### 5.3 RefCell → Mutex 的语义变化（关键认知差）

| 维度 | 现状 `RefCell` | 改造后 `Mutex` |
|---|---|---|
| 跨线程 | 不允许（单线程类型） | 允许（本卡目的） |
| 双重借用 | **运行时 panic**（`borrow` 后再 `borrow_mut` 直接炸，有保护） | **无此检查**——换成「持 guard 跨阻塞/跨 CEF 调用」的**死锁**风险（坑①） |
| 现状是否真有双重借用 | **没有**。全库都是「一个 `.with` 闭包内单次 borrow，闭包结束还」，顺序多个 `.with` 不构成嵌套（已逐处核：switch_tab/close_tab/apply_zoom/refresh_tabbar 皆如此） | 所以换 Mutex **不新增借用错误**，只把「借用检查」换成「持锁纪律」 |
| 失败表现 | 借错 → panic（当场炸，好查） | 锁错 → 死锁（静默卡死，难查） |

**结论**：RefCell→Mutex 不引入新的「二次借用」bug（现状本就没有嵌套借用），但**把「运行时会炸」换成了「运行时可能静默死锁」**。所以改造后**死锁比借用更难发现**，二狗实编/真机时：
- 每个状态锁 guard 控制在单表达式内（clone 出数据/句柄立即 drop）。
- `cef_ui`/`cef_ui_call` 永远在锁外。
- 真机回归时**盯「窗口卡死不响应」这个症状**——那是死锁的表象，不是「慢」。

### 5.4 `Client`/`Browser` 保活（SHELL_CLIENTS / CLIENTS_ALIVE）跨线程后会不会二次借用 panic

**不会**（两个原因）：
1. 它们是纯 `Vec<Client>` 保活容器，**只 push、从不 `borrow` 出 client 再调其方法**（client 由 CEF 内部持有引用，本模块不直接调 client 方法）——不存在「借用 client」这回事，谈不上二次借用。
2. 换 `Mutex<Vec<Client>>` 后，即使将来有人 `lock` 取出 clone 一份 client，`Mutex` 也没有 RefCell 那种 borrow 计数检查，最多是「持 guard 跨 CEF 调用」的坑①（用 5.1 纪律规避），**不会触发 RefCell 式二次借用 panic**。
- 唯一要注意：`Client` 是 `RefGuard`（Send+Sync），clone 一份进 `Mutex` 合法；保活语义不变。

## 7. 风险与未把握（如实）

1. **`Task` 构造的最终写法需二狗实编确认**：`wrap_task!` 宏的 `execute` 方法签名、以及 `f: FnOnce` 在 `&self` 下如何存（`RefCell<Option<…>>` vs `Box<dyn Fn()>`）——我给了模式与 API 行号，但没实编（不占编译窗口）。4.2 是伪码，二狗落地时以 crate doctest（bindings :29539）为准。
2. **`run_toolbar_js` 是否改为「自身 cef_ui 安全」是设计选择**：我推荐它内部判 `currently_on`（调用方零改动，最省），但也可让 20+ 调用方逐处包——二狗选前者更稳。
3. **`apply_toolbar_height`/`refresh_tabbar` 的 GTK 主定时器入口**（shell.rs:552-558、cef_cmd.rs:431-434）改造后是「读共享 SHELL_TABS（Mutex）+ cef_ui 跑 run_toolbar_js」。这里有个微妙点：定时器本身仍在 GTK 主线程触发（glib local 不会迁到 CEF UI），**这是符合预期的**——读纯数据在 GTK 主 OK，动句柄投 CEF UI。二狗别误以为定时器要迁。
4. **`open()` 的异步窗口句柄时序**：open 同步建 view，但 `SHELL_WINDOW` 要等 on_window_created（CEF UI 回调）才登记。multi_threaded=1 后这个回调在 CEF UI 线程写 `Mutex<Option<Window>>`，而 force_show（GTK 主，open 之后立刻调）可能先于 on_window_created 跑到 → force_show 读到 `None`（走 565 行「没有窗口句柄」warn）。**现状就是这个时序**（open 后立刻 force_show，靠后续 glib 定时器补推），改造不引入新问题，但二狗真机若见「窗口没出来」，先查这里而非锁。
5. **CPU 目标达成度不保证**：本卡只保证「线程模型改对、不跨线程 panic/死锁」。multi_threaded=1 实测 5.5% 是方案实验值，是否稳定复现归二狗真机（方案表第 6 行已证 `--renderer-process-limit=3` 会崩，别回退那条）。
6. **未实编、未真机**：本报告全部结论来自静态读码 + cef crate 源码核对（行号为准），**没有跑过 cargo、没有真机**。凡「已验证」均指「源码/类型层面静态确认」，非运行时验证。
