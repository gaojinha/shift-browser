### 二、U-4 排查与阻塞说明（⚠️ 阻断待拍板）

#### 1. 排查过程与底层现状
- **派单假设**：认为 `engine/content_filter.rs` 存在未暴露给前端的拦截计数钩子（`status()` 包含拦截数）。
- **源码实测**：
  - 查阅 `content_filter.rs:253-263`，`status()` 函数内容为：
    ```rust
    pub fn status() -> serde_json::Value {
        let ready = cached().lock().unwrap_or_else(|e| e.into_inner()).is_some();
        serde_json::json!({
            "ready": ready,
            "enabled": is_enabled(),
            "rulesBytes": RULES_LEN.load(Ordering::Relaxed),
            "ruleCount": BUILTIN_URL_RULES.len(),
        })
    }
    ```
    该状态仅记录规则编译就绪状态、开关、规则字节数及内置规则条数，**并不包含拦截事件或命中计数**。
- **WebKit 机制限制**：
  - WebKitGTK 的 `WebKitUserContentFilterStore` / `WebKitUserContentManager` 采用内核层静默过滤（`webkit_user_content_manager_add_filter`）。
  - WebKit 官方 C API **并未暴露资源被 Filter 拦截时的信号（Signal）或事件回调**，`resource-load-started` 信号仅在请求发起前触发，无法直接获取内容过滤器的匹配拦截命中事件。

#### 2. 建议解决方案（供二狗/高哥决策）
1. **方案 A（建议）**：UI 口径明确说明，不强求网络层实时拦截计数；面板展示“已装载规则数（如 12 条网络规则） + JS 注入拦截数”。
2. **方案 B**：未来通过编写独立的 WebKitWebExtension 进程插件（C/Rust），拦截所有网络资源请求并自主维护规则匹配器（工作量极大，超出精修范围）。
