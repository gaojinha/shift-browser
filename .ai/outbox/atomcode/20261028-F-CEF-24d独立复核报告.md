## 复核④：风险点（按严重度，均需真机验证）

**R1（中）`cef_ui_call` 在 CEF 未初始化/销毁窗口 panic**
- `cef_ui.rs:119-120`：CEF 初始化前/销毁后调 `cef_ui_call` → post 未入队 → mpsc 无回传 → panic。
- 正常流程不触发（CEF 初始化后才调）；异常路径（CEF 初始化失败）panic。panic 是显式失败（可接受），建议 CEF 初始化失败时不调 `cef_ui_call`。

**R2（低，已静态确认无死锁点）Mutex 同锁重入死锁（24b thread_local→Mutex）**
- `lock_state`（`shell.rs:436-438`）毒化降级只防中毒、不防死锁（死锁 = lock 永久阻塞，降级不生效）。
- **静态确认**：全库 **62 个 `lock_state` 调用点**（SHELL_TABS 36 / SHELL_WINDOW 9 / 其余 17）——核了 3 个持锁较久的（`1761` move_tab / `1792` toggle_tab_pin / `1807` toggle_tab_mute）实为 `{ let mut t = lock_state(...); ... }` **块内锁**（块结束即释放，块内不嵌套、不传递锁），其余从一致模式（`let x = { let t = lock_state(&SHELL_TABS); t.get(...) }`）确认为块内/语句级锁。**结论：静态层面无同锁重入死锁点**。
- 剩余风险：真机并发时序（Mutex 保单操作、复合操作中间态由 `get(active)` 兜底）——需真机盯"窗口卡死"，但**非静态死锁**。

**R3（低-中）CEF 回调链完整跨线程行为**
- `on_window_created`/`on_after_created`/`on_before_close` 体内无裸 GTK 调用（复核②），但回调内部调用函数（`refresh_bookmarks_ui` 等）的完整跨线程链需真机验证。

**R4（低）BOOKMARKS 跨线程（预审发现的隐性 bug）**
- `cef_cmd.rs:168`（tokio 写）/ `shell.rs:482`（Mutex）。24b 改 Mutex → 数据竞争消除，安全。

**R5（低）并发时序**
- Mutex/Atomic 保护单操作；复合操作（ACTIVE_TAB+SHELL_TABS 非原子）中间态由 `get(active)` 兜底。
