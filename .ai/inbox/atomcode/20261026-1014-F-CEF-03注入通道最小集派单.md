# F-CEF-03 第一步：CEF 侧 JS 注入通道「最小可用集」

**只做这一件事，做完立刻交付。** 你前两轮都在 30/60 分钟内被超时杀掉、零产出，
所以本轮范围压到最小：**只验证「能往页面注入一段 JS」这一条链路**，不做扩展系统、不做广告拦截。

## 为什么现在做这个

协调器同轮实测（`.ai/evidence/20261026-0138-协调器自采-CEF新构建同轮对照.md` §4）确认，
CEF 与真 Chrome 的**头号真实差异**是：

- 真 Chrome：`navigator.userAgentData.brands` = `Chromium 154` + **`Google Chrome 154`** + `Not A(Brand 99`
- CEF 只有两项，**缺 `Google Chrome`** —— 而 UA 头写着 `Chrome/154.0.0.0`，
  品牌表与 UA 自洽性断裂，是风控专门比对的点

修它需要注入通道（仓库里 `privacy.js:357/364` 已有拦截逻辑，等通道把值送进去）。
所以**通道是当前关键路径**，卡着 F-CEF-08。

## 本轮目标（就一条）

让任意加载的网页在 `document_start` 阶段拿到一段我们注入的 JS。

**验收标准（真机）**：
1. `cargo build --features cef-engine` 后启动实例（参考命令见下）
2. 导航到 `https://example.com`
3. 用 CDP 在页面里求值 `window.__SHIFT_INJECT_OK__`，应返回 `true`
4. 控制台/日志能看到注入执行记录

## 实现提示（先查证再动手）

- CEF 侧有两个可落点：`CefRenderProcessHandler::on_context_created`（渲染进程，真正的 document_start）
  或 `CefLoadHandler::on_load_start`（浏览器进程，用 `frame.execute_java_script`，晚一点点但更简单）
- **建议先走简单的**：`on_load_start` 里对 main_frame 执行 `execute_java_script`，脚本第一行写
  `window.__SHIFT_INJECT_OK__ = true;`。跑通了再考虑换 render 进程（那需要 `multi_threaded_message_loop` 或独立 render 进程 handler，工作量大）。
- 现有 `browser.rs` 的 `CefTabLoadHandler` 已实现 `on_loading_state_change`，同处可加 `on_load_start`。
- 注意：**不要在 on_load_start 里做重活**（会拖慢首屏），本轮只注入一行标记。
