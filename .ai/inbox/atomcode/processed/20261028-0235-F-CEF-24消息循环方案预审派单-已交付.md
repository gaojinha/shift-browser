## 背景（照 `docs/F-CEF-24-CPU优化方案_2026-10-27.md`）

- 安装版 release 主进程 CPU 64–85%，debug 100%。根因 perf 栈已钉死：CEF 在 GLib 主循环注册的 X11 source 忙轮询（`gtk_main_iteration_do → g_main_context_iteration → xcb recvmsg → libcef HasPendingResponses`）。
- 实验数据（表里 6 行）：`multi_threaded_message_loop=1` CPU 直接掉到 **5.5%**，但窗口操作跨线程 panic；`external_message_pump=1` 时 CEF 不调用 `OnScheduleMessagePumpWork`（0 次）。
- 定稿方案 6 步：① `multi_threaded_message_loop=1` ② `SHELL_TABS`/`BROWSERS`/`SHELL_TOOLBAR_VIEW` 等 thread_local 改全局 Mutex/OnceLock ③ 所有 CEF 调用投递到 CEF UI 线程（`post_task(TID_UI, …)`，包 `cef_ui(||…)` 辅助）④ 关键调用点清单（force_show / apply_toolbar_height / run_toolbar_js / new_tab / close_tab / switch_tab / handle_action）⑤ 回调线程保持 ⑥ 回归清单。

## 你的交付（一份预审报告，写进 `.ai/outbox/atomcode/`）

1. **thread_local 全量清单**：`grep` 出 `engine/cef/` + `cef_cmd.rs` 里所有 `thread_local!` 静态（现在至少 3 处：`shell.rs:343` 一大坨（SHELL_CLIENTS/SHELL_WINDOW/SHELL_LAYOUT/SHELL_TOOLBAR_VIEW/SHELL_TABS/ACTIVE_TAB/TAB_SEQ/SHELL_CACHE_DIR/CLOSED_URLS/zoom 等）+ `shell.rs:2068` LAST_FIND_TEXT + `browser.rs:15`（BROWSERS/CLIENTS_ALIVE/PENDING_SIZE）+ `cef_cmd.rs` 里的 Browser 句柄），逐个标注：
   - 谁会写、谁会读（回调线程？主线程？tokio？），
   - 改成 `Mutex<RefCell<…>>` 还是 `OnceLock<Mutex<…>>` 还是 `RwLock` 的建议（注意：CEF 回调现在跑在 CEF UI 线程，`post_task` 之后主线程和 CEF UI 线程都会碰这些量，**锁粒度要小、不许在锁里再 post_task 防死锁**——这是方案文档第 43 行风险条）；
