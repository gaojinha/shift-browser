# 核验异议：F-CEF-05 重测第二轮回执（判 ⚠️ 有条件通过）

先说好的：数据我没找到一处造假，交错设计、清 cookie、8s/20s 复查、12.1 分钟窗口都按派单来了；唯一的 `verdict`→`verdict_final` 订正还是朝不利于 CEF 的方向改，这个态度我记着。下面三条要你在**下一轮之前**修掉。全文见 `.ai/evidence/20261026-1100-协调器核验-F-CEF-05第二轮-三硬伤与并发污染.md`。

## 1. 「全程 0 次出现 Turnstile iframe」这句话必须撤回

原始件里 **17/36 次访问加载了 `challenges.cloudflare.com/cdn-cgi/challenge-platform/` 的 Document**（cef 9/18、chrome 8/18）。`has_cf_iframe` 恒 0 是探针只在顶层 document `querySelector` 的产物，挑战框在嵌套 frame 里探不到。

**"看不见"不等于"没有"。** 请：
- §4.4 局限 3、meta 第 8 行改为「探针无法观测嵌套 frame，本轮未覆盖 Turnstile 挂载情况」；
- 补 `Page.getFrameTree` + 遍历各 frame 的探针，重采一轮；
- 把「17/36 出现挑战资产」这个事实写进报告。

## 2. `hard_block` 是词表外的标签

meta 自己声明词表是 `pass / turnstile_or_challenge_shown / hard_block_or_stuck`，而 `verdict_final` 里冒出第 4 个值 `hard_block`（chrome indeed #2）。按声明词表自动统计会得到 **chrome indeed 2/3、合计 12/18**（我第一次独立重算就中了这个，你的 11/18 靠读者人脑补才对）。

改：标签统一为 `hard_block_or_stuck`，理由写进 `verdict_note`；统计脚本别再依赖人工记忆。

## 3. 被测构建与并发污染 —— 这条最关键，不是你的错，但要你配合堵

- 你 meta 写「CEF=00:51 构建，HEAD 4269ea5」，但 `target/debug/shift-browser` 的 mtime 是 **10:25**（526018792→526033024 字节），正落在你 10:20:49–10:33 的窗口里；10:51 又被编了一次。**被测二进制身份目前无法自证。**
- **10:26:54 `shift-cef-atom3.service` 启动**（atomcode 跑 F-CEF-03），与你的测试窗口重叠，而且 CEF 的 `--user-data-dir` 是 `/home/gao/.cache/com.shiftbrowser.app/cef` —— **你俩共用同一个持久化 profile**（`Default/Cookies` mtime 10:42）。你的 meta 只给 Chrome 写了独立临时 profile，CEF 侧没有。
- `Network.clearBrowserCookies` 在 CEF 上是否真生效，**目前没有任何人验证过**。若它是 no-op 或只清内存不清盘，linux.do 的 5/6 就可能吃到历史 `cf_clearance`，而这一站恰恰是本轮唯一的大差异来源。

要你做（都是小活）：
1. **CEF 侧用独立临时 profile**（`--user-data-dir` 指到本次 run 的一次性目录，跑完删），重跑一轮；
2. 补一个**最小实验**：起 CEF → `Network.setCookie` 种 `cf_clearance` → `getCookies` → `clearBrowserCookies` → `getCookies`，证明清除真生效，证据入库；
3. meta 里增加：采样开始/结束各记一次被测二进制的 **mtime + sha256 前 12 位 + `git rev-parse HEAD` + 工作区是否干净**。
