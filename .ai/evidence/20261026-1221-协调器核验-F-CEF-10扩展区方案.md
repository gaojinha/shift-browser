## 二狗的增量结论（copilot 没写到，5 条）

### 1【量级比"图标是摆设"重得多，且**自证通道也一起断**】
`inject_extensions`（`src-tauri/src/extensions.rs:114`）是**用户脚本 + 隐私 JS + 广告拦截 + compat + WebMCP + 翻译桥的统一入口**，它靠 `app.get_window("main")` → `window.webviews()`，CEF 独立窗口拿不到。而 CEF 侧 `grep extensions` **零命中**，页面注入只有 `browser::inject_marker`（brands + `__SHIFT_INJECT_OK__`）；`shell.rs:900/986` 那两处 `execute_java_script` 是 `run_toolbar_js`（刷书签栏/标签栏 UI），**不是页面注入**。
更狠的一层：连**验证注入是否生效的自检也走不通**——`PRIVACY_SELFTEST_JS` 经 `extensions/privacy.rs:308` 的 `engine::webview::eval_js_with(&pwv.inner(), …)` 执行，同样是 Tauri webview 通道。所以 CEF 下的真实状态是「整套隐私/拦截/用户脚本能力为 0，**且无法自证**」，不是 UI 层面的小毛病。

### 2【应用内自检会掩盖这个缺口】
`selfcheck.rs:326` 只 `SELECT COUNT(*) FROM extensions WHERE enabled=1`，然后**无条件** `CheckItem::ok("启用扩展", "{n} 个")`（连 Err 分支也返回 ok("未知")）。它报**数量**不报**是否注入**。后遗表现：CEF 下用户挂了 3 个扩展，自检依然全绿。F-CEF-11 做完后，这个检查项得加「引擎 + 注入生效」维度，否则等于给缺口发通行证。

### 3【F-CEF-11 验收没有样本数据，得先造】
本机实测 `extensions` **0 行**、`userscripts` 也 **0 行**（`adblock_rules` 表根本不存在）。而 F-CEF-11 派单的验收要「检查 `ADBLOCK_INJECTIONS` 计数增长」「隐私标记存在」——没有已启用条目，注入通道做完也只能证"代码跑了"，证不了"行为生效"。建议验收前置一步：**建一条用户脚本 + 造一个最小 manifest 目录 load 进去**，再跑 CDP 求值。这条不写清，60 分钟一定不够。

### 4【现成通道在 `browser.rs:209 eval_js`，别新写】
`pub fn eval_js(browser, script)`（script_url 标 `shift://inject`）已具备，但带 `#[allow(dead_code)]` 且**全仓零调用点**。F-CEF-11 直接复用它 + 去掉 dead_code 即可，比在 `on_load_start` 里手搓 `frame.execute_java_script` 省一层。

### 5【注入点必须挂两处，只挂一处会漏页面】
`on_load_start` 有**两条实现**：`browser.rs:309` 与 `shell.rs:1230`。`shell.rs:1229` 的注释已经写明「与 CefTabClient 是两条路径，**注入点必须各挂一份**（共用 `inject_marker`）」——`inject_marker` 就是这么处理的。F-CEF-11 派单只说「`on_load_start` 里取缓存」，按字面只改一处，新建标签那条路径就会**静默漏注入**。验收必须两条路径各测一次。

另：派单写 `collect_enabled_items` 产出 `(Vec<(Option<String>,Option<String>)>, bool)`，真身 `adblock.rs:84-86` 返回的是 `Result<(…), String>`，外面套着 Result，实现时记得解包。
